# Changelog: Rose (project level)

Format: date, what changed, why. Newest first.

## 2026-08-15

- Endpoint IPC increment 2 built: Call and Reply syscalls added on top of increment 1's Send/Receive, so a task can now send a message and block waiting for a specific response instead of just fire-and-forget (full writeup in `docs/cores/kernel/CHANGELOG.md`). A Reply capability is minted per outstanding Call and handed to whichever task receives it, the only way to answer that specific request. Zero build warnings. Booted clean on QEMU BIOS and UEFI: both runs confirm Send, the second Receive, and the Reply syscall itself, then truncate right before Call's own final resume line, the same pre-existing timer-preemption limitation already known from increment 1, one hop further out; not a regression. Not yet run in Oracle VM VirtualBox, so the full round-trip and the new cross-family aggregate report (now living on Call instead of Send) aren't confirmed under real hardware preemption yet.

## 2026-08-09

- Kernel security audit: 5 parallel independent review passes across the whole `kernel/src/` tree (boot/interrupts, memory/paging, capabilities, scheduler/usermode, syscall dispatch/PCI), weighted toward memory safety, capability/privilege correctness, and interrupt-safety rather than typical logic bugs, on the reasoning that this is unsafe systems code where a bug can mean a privilege boundary crossed, not just a wrong answer. Two passes converged independently on the same root vulnerability from different angles; two others independently found the same rights gap. 5 real bugs found and fixed same day, full writeups in `docs/cores/kernel/BUGS.md`:
  - **Ring-3 privilege escalation via SYS_FRAME_MAP.** Three compounding gaps: no check that a caller-supplied vaddr stays out of the PML4 range every AddressSpace shares by physical reference with the kernel's own tables (could overwrite kernel `.text`, executable, from ring 3, with only the default rights Retype already grants); `paging::next_level` never checked for a huge-page leaf before treating it as a table pointer (arbitrary physical memory corruption via any HHDM-range vaddr); neither Frame-Map nor Configure rejected the kernel's own AddressSpace as a target. Closed with three independent mechanisms (`paging::is_shared_vaddr`, `AddressSpace::is_kernel`, an `assert!` in `next_level`), kept all three deliberately rather than relying on one.
  - **W^X bypassable through the same syscall**: a writable Frame-Map request didn't force NX, so a page could be simultaneously writable and executable. Now forces NO_EXECUTE whenever WRITABLE is requested.
  - **Deadlock risk under real hardware preemption**: `spawn`/`spawn_in`/`spawn_user`/`with_current_cspace` locked the scheduler with no cli guard despite being called after interrupts are enabled; a real tick landing mid-critical-section would spin `tick()` forever against a lock the interrupted code could never release. Fixed with a proper save-flags/cli/restore-flags pair (not a blind cli/sti -- some of these are also called from inside the syscall interrupt handler itself, where a blind `sti` would be wrong).
  - **Configure destroyed a caller's CSpace on a failed re-Configure**: `take_cspace` (irreversible) ran before the "already configured" check. Reordered to verify first, matching this kernel's own "verify before commit" design principle.
  - **Untyped Retype ignored capability rights**: every other syscall gates on a specific right; Retype checked only object_type. A rights-narrowed Untyped cap didn't actually confine Retype. Not yet exploitable (no cross-CSpace delegation in v0.1) but closed before IPC makes it one.

  All five fixes verified with `cargo check`/`cargo build --release` (clean, zero warnings) and by hand against the existing self-test's actual call sites (confirmed none of the new checks fire on legitimate self-test traffic). Booted clean on QEMU BIOS and UEFI, all self-test steps pass, identical result both paths. Confirmed in Oracle VM VirtualBox: same full sequence passes on real hardware, including 50 genuine hardware timer ticks during boot with no hang. That last point is a no-regression result, not a targeted proof of the deadlock fix; the self-test's normal boot path doesn't force a tick to land inside the exact critical sections that fix guards, see `BUGS.md` for the specific finding. Promoted to `stable` (a683694). Also fixed a stale `BUGS.md` citation found in passing (the vector-0x80 gate's `type_attr` byte was documented as 0x8E; the code actually uses 0xEE, the underlying "genuine interrupt gate" claim was already correct, only the specific hex value was wrong).

- Endpoint IPC increment 1 built: an Endpoint object plus blocking Send/Receive syscalls, register-only, no Call yet (full writeup in `docs/cores/kernel/CHANGELOG.md`). Zero build warnings. Receive-side delivery confirmed on QEMU BIOS and UEFI (the self-test's second task correctly receives the first task's blocked Send message). The first task's own resume after being woken, and the self-test's final aggregate report, depend on a real timer preemption to complete; this dev sandbox's QEMU/TCG never delivers real hardware IRQ0 (already documented in `docs/cores/kernel/TROUBLESHOOTING.md`), so that line can't be observed here. Confirmed this is the same pre-existing, already-known sandbox limitation seen in earlier features, not a new bug; no scheduler or IPC code was changed to work around it. Confirmed in Oracle VM VirtualBox: fresh serial log shows real hardware timer ticks interleaved throughout, the Send self-test step passing, and ends with `usermode self-test: full boot sequence confirmed`. Round-trip works correctly under real preemption; the QEMU/TCG gap was purely a sandbox artifact, not a defect.

## 2026-08-08

- Per-task kernel entry stacks added: fixes the page-fault bug logged below. Every task previously shared one single kernel-mode stack for the moment it traps from user mode back into the kernel; that was safe with only one such task, but code reading confirmed the fault only became possible once a second one existed and started alternating with the first through that same shared buffer, each risking clobbering the other's paused state. Each task now gets its own dedicated stack for this, permanently, closing that gap. Zero build warnings. Verified on QEMU BIOS and UEFI, all self-test steps pass clean. Confirmed in Oracle VM VirtualBox: the second task now survives its own first syscall and keeps running, no fault, the first time two independently-scheduled ring-3 programs have coexisted successfully under real hardware preemption. Promoted to `stable` together with the two entries below.
- Frame-Map syscall added: a task can now map a physical frame it holds a capability to directly into a target address space, at whatever virtual address and read/write/execute permissions it chooses (within what its capabilities allow). This closes the page-fault bug logged below: the second self-test task's code and stack were previously only mapped into the wrong address space (a stale comment claimed it was the same one Configure would run the task in; it wasn't), so once a real timer preemption actually scheduled that task, it faulted immediately. The two pages now get mapped into the actual address space Configure targets via this new syscall, before Configure ever runs. Turned out smaller than first estimated: reusing an already-existing spare page meant no memory pool growth was needed. Zero build warnings. Verified on QEMU BIOS and UEFI, all self-test steps pass including the two new mapping steps, no fault. Promoted to `stable`; see the PCI/Frame-Map/per-task-stacks merge above.
- Kernel design principle written down: verify before commit. Codifies the pattern already used by Configure (check a thread's state before claiming it) as a standing rule for future syscalls and hardware-facing code, nothing acts on unconfirmed information. Documentation only, no code change.
- PCI enumeration added: the kernel can now walk the PCI bus and read what a device publishes about itself, vendor id, device id, class code, subclass, programming interface, through the same legacy I/O ports every PC-compatible x86 machine has supported since the original PCI spec. Read-only, no device is ever sent a command, and every slot's vendor id is checked before anything else about it is read, the same verify-before-commit shape as the new design principle above. This is the first piece of the hardware detection model discussed for letting Rose recognize standardized, self-describing hardware without needing vendor-specific drivers; PCI's class/subclass/prog-if codes are the first of those self-describing mechanisms to actually get read. Zero build warnings. Verified on QEMU BIOS and UEFI: correctly enumerates QEMU's own standard i440FX chipset devices (host bridge, ISA bridge, IDE, ACPI/PM, VGA, e1000 NIC), identical result both boot paths.
- Run in Oracle VM VirtualBox: PCI enumeration passed clean, correctly reading 10 real devices, several kinds never seen on QEMU (an AMD NIC, VirtualBox's own VGA and Guest Additions devices, USB controllers), confirming the code reads genuine config space rather than anything QEMU-specific. Right after, the kernel faulted and halted. Not a PCI bug; a pre-existing gap in the Configure feature (2026-08-01) that this run was simply the first to reach, since VirtualBox's real hardware timer preempts into the Configure-spawned second task where this sandbox's QEMU/TCG doesn't. Logged as an open bug in the kernel core's BUGS.md, since fixed and merged to `stable` above.

## 2026-08-01

- Task 0 address-space sync fix added: task 0's own scheduler bookkeeping now stays in sync when the usermode self-test manually switches into a second AddressSpace before dropping to ring 3. Before this, that switch changed CR3 but never told the scheduler, so the next real timer preemption that cycled back to task 0 reloaded CR3 from a stale field instead, reverting to the kernel's own AddressSpace mid ring-3-program. This is what caused the page fault crash logged below in the Untyped/Retype entry's Oracle VM VirtualBox run. Zero build warnings. Verified on QEMU BIOS+UEFI, no regression in the existing ten-step self-test. QEMU never delivers real hardware timer interrupts in this sandbox, so this fix couldn't be exercised for real preemption there. Confirmed in Oracle VM VirtualBox: full ten-step self-test now passes clean end to end with real hardware timer ticks interleaved throughout, no fault. Promoted to `stable`.
- Capabilities/CSpace v0.1 added: a new `abi` crate shared between the kernel and future userspace defines `ObjectType`, `Rights`, `Capability`, `CPtr`, and `KernelObjectId`, matching the kernel core's spec doc. Added `CSpace` as an object type that the spec was missing despite already granting one at boot handoff. A fixed 64-slot `CSpace` supports copy, mint, move (within one CSpace for now), and revoke, with a derivation tree so revoking a capability cascades to everything copied or minted from it. A boot self-test grants a capability over the kernel's own address space, copies it, moves the copy, mints a narrowed-rights badged derivative, revokes the original, and confirms every descendant slot cleared. Not wired to any syscall yet, no component owns a CSpace yet, and cross-component Move still needs IPC, which doesn't exist yet; each is its own future feature. Zero build warnings. Verified on QEMU BIOS+UEFI. Not yet run in Oracle VM VirtualBox.
- CSpace syscalls added: every task now owns a CSpace, and a ring-3 `int 0x80` can reach copy/mint/move/revoke on it (new syscall numbers, args in rdi/rsi/rdx/r10, result in rax, 0/positive success or a negative error code). The interrupt handler frame is now mutable so a syscall's result can actually be written back into the caller's rax before returning. The usermode self-test's ring-3 program now runs a fixed six-step CSpace sequence (copy, move, mint, a copy that correctly fails with dest-occupied, a revoke, then a copy that correctly fails with source-empty) against a capability granted into the task's own CSpace ahead of time, standing in for real boot handoff. Zero build warnings. Verified on QEMU BIOS+UEFI: all six steps pass with expected results. Not yet run in Oracle VM VirtualBox.
- Untyped/Retype v0.1 added: Untyped is a pool of individually-allocated physical frames, not one contiguous region yet. Retype pops a frame off that pool and turns it into a Frame or CSpace, the only two retypeable types for now. Reached via a new ring-3 syscall (0x1004): checks the source cap is really Untyped, the requested type is retypeable, and the destination CSpace slot is empty, all before touching the pool, since a frame handed out can't go back in if the install after it is rejected. A new CSpace operation installs the freshly retyped capability as a child of the Untyped cap in the same derivation tree copy/mint already use, so revoking the Untyped cascades into anything retyped from it. The usermode self-test's ring-3 program now runs four more syscalls after the six CSpace ones: retype a Frame, retype a CSpace, then deliberately exhaust the two-frame pool and deliberately request an unsupported type, both expected to fail cleanly. Zero build warnings. Verified on QEMU BIOS+UEFI: all four steps pass with expected results. Run in Oracle VM VirtualBox: the first three Retype steps passed with correct results, then a real hardware timer preemption reverted CR3 to the kernel's own AddressSpace mid-sequence and the CPU faulted on the next ring-3 instruction fetch; a pre-existing scheduler/AddressSpace gap this feature's longer ring-3 program was the first to run long enough to expose, not a bug in Retype's own logic (open, see kernel core's BUGS.md).

## 2026-07-25

- Scheduler made address-space-aware: each task now carries the `AddressSpace` it runs in, and both the timer-tick and voluntary-yield switch paths reload CR3 for the incoming task right before the existing register swap. `spawn` still defaults every task to the kernel's own AddressSpace; a new `spawn_in` picks a specific one. A new self-test spawns one task per AddressSpace, each writing a different pattern to the same virtual address backed by a different physical frame, and confirms both only ever read back their own pattern after several real preemptions interleaved with other running tasks, proving CR3 actually follows the task under real scheduling rather than a single manual switch. Closes the gap flagged in the address-spaces entry below: the scheduler can now genuinely run components in separate AddressSpaces. Doesn't touch capabilities yet, so nothing stops a task from calling kernel functions directly today; that's the next layer. Zero build warnings. Verified on QEMU BIOS+UEFI and confirmed in Oracle VM VirtualBox, identical isolation result with real hardware timer ticks interleaved in. Promoted `main` to `stable`.
- Address spaces added: page tables are now built around an `AddressSpace` handle instead of one implicit global table set. `new_address_space()` builds a fresh one sharing the kernel/HHDM upper half (present, supervisor-only) with a private, zeroed lower half. `map_page`/`unmap_page`/`switch`/a new read-only `is_mapped` check are all methods on it now. The usermode self-test moved into a real second AddressSpace, writing its program in through the target frame's permanent HHDM alias instead of through the not-yet-active user virtual address, which also retires the earlier WRITABLE-then-remap workaround from the ring3 feature (kept in `BUGS.md` as history, noted here as the reason it's obsolete). A new self-test proves two AddressSpaces are actually isolated from each other and that switching CR3 between them and back works. Documented two known gaps rather than fixing them yet: the kernel/HHDM sharing is present-but-supervisor-only, not yet the stricter "structurally unmappable" goal in the kernel README; and the scheduler's context switch still never touches CR3, fine while every task shares the kernel's own AddressSpace, but blocking before multiple components can each run in their own. No teardown/free for an AddressSpace yet, same accepted category of scope cut as the heap's no-coalescing. Zero build warnings. Verified on QEMU BIOS+UEFI and confirmed in Oracle VM VirtualBox, identical serial log including real hardware timer ticks. Promoted `main` to `stable`.
- Ring 3 / user mode added: kernel drops to CPL3 for the first time, via new user GDT selectors, a syscall gate at IDT vector 0x80 (DPL=3, only that one gate), and a `PAGE_USER` fix so the U/S bit actually propagates through every level of the page-table walk, not just the leaf. A hand-written asm program (not compiled Rust; no user-mode runtime exists yet) makes two round-trip `int 0x80` syscalls, then parks for good after the kernel logs and halts on the second one. No process model, no way back into the interrupted kernel flow, no second user task; all deliberate v0.1 scope cuts. Hit and fixed one real bug: the kernel's own copy into the user code page needs WRITABLE set regardless of ring, CR0.WP doesn't check CPL. Zero build warnings. Verified on QEMU BIOS+UEFI and confirmed in Oracle VM VirtualBox (identical two-syscall sequence and halt line). Promoted `main` to `stable`.
- Kernel boot verified in Oracle VM VirtualBox, matching QEMU serial output. Promoted `main` to `stable` (see `BRANCHING.md` merge log).
- Memory bring-up: kernel parses Limine's memory map and logs every region over serial. Physical frame allocator built on top (free-list, HHDM-addressed, self-test on boot). Verified on QEMU BIOS+UEFI and Oracle VM VirtualBox. Promoted `main` to `stable` again (see `BRANCHING.md` merge log).
- GDT/IDT and kernel-owned page tables added (all 32 exception vectors, double-fault IST stack, W^X kernel image mapping, HHDM remap, map/unmap self-tests). Verified on QEMU BIOS+UEFI and now in Oracle VM VirtualBox too, serial logs match exactly. Promoted `main` to `stable`.
- Kernel heap added (free-list first-fit, 1MiB fixed region, backs `extern crate alloc`). Self-test exercises Box and a growing Vec, confirms memory returns on drop. Verified on QEMU BIOS+UEFI and Oracle VM VirtualBox. Promoted `main` to `stable`.
- PIC + PIT timer added (IRQ0 remapped to vector 32, 100Hz). Hardware IRQ0 never reaches the CPU in this dev sandbox's QEMU/TCG despite verified-correct PIC/PIT programming; confirmed via a VirtualBox boot (real hardware virtualization) that this is a sandbox-only limitation, not a kernel bug, since the tick handler fired and the counter advanced normally there. That same VirtualBox run also surfaced a real bug in the self-test's own timeout math (frequency floor instead of ceiling, caused an early false negative on fast hosts); fixed. Boot self-test is timeout-bounded with a software-interrupt fallback so it never hangs in this sandbox. Verified on QEMU BIOS+UEFI and boot-chain-verified through the timer stage in Oracle VM VirtualBox. Promoted `main` to `stable`.
- Scheduler v0.1 added: task struct, hand-written context switch (naked asm), single round-robin queue, timer-tick and voluntary-yield preemption paths. Cooperative two-task self-test proves round-robin switching works independent of whether hardware timer interrupts fire at all. Hit and fixed three real bugs during bring-up: a fabricated stack frame written in the wrong order (crashed with a page fault at rip=0); a self-test task that stopped yielding after finishing (froze the whole round-robin ring); and a boot-order bug that only a VirtualBox run on real hardware exposed, where the first hardware timer tick landed before the scheduler was initialized and panicked on a modulo by zero (this sandbox's QEMU/TCG never delivers a real IRQ0, so it never hit this). Verified on QEMU BIOS+UEFI, zero build warnings, and confirmed in Oracle VM VirtualBox for the boot-order fix specifically (same result, no panic). Promoted `main` to `stable`.
- Added a countdown to the timer self-test's ~2s wait (serial output) and to `smoke-test.sh`'s fixed boot wait (terminal output), so a slow wait doesn't look identical to a hang. Only visible in this sandbox's software-int-fallback path; real hardware finishes the wait too fast to ever reach it.
