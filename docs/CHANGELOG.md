# Changelog: Rose (project level)

Format: date, what changed, why. Newest first.

## 2026-08-01

- Capabilities/CSpace v0.1 added: a new `abi` crate shared between the kernel and future userspace defines `ObjectType`, `Rights`, `Capability`, `CPtr`, and `KernelObjectId`, matching the kernel core's spec doc. Added `CSpace` as an object type that the spec was missing despite already granting one at boot handoff. A fixed 64-slot `CSpace` supports copy, mint, move (within one CSpace for now), and revoke, with a derivation tree so revoking a capability cascades to everything copied or minted from it. A boot self-test grants a capability over the kernel's own address space, copies it, moves the copy, mints a narrowed-rights badged derivative, revokes the original, and confirms every descendant slot cleared. Not wired to any syscall yet, no component owns a CSpace yet, and cross-component Move still needs IPC, which doesn't exist yet; each is its own future feature. Zero build warnings. Verified on QEMU BIOS+UEFI. Not yet run in Oracle VM VirtualBox.
- CSpace syscalls added: every task now owns a CSpace, and a ring-3 `int 0x80` can reach copy/mint/move/revoke on it (new syscall numbers, args in rdi/rsi/rdx/r10, result in rax, 0/positive success or a negative error code). The interrupt handler frame is now mutable so a syscall's result can actually be written back into the caller's rax before returning. The usermode self-test's ring-3 program now runs a fixed six-step CSpace sequence (copy, move, mint, a copy that correctly fails with dest-occupied, a revoke, then a copy that correctly fails with source-empty) against a capability granted into the task's own CSpace ahead of time, standing in for real boot handoff. Zero build warnings. Verified on QEMU BIOS+UEFI: all six steps pass with expected results. Not yet run in Oracle VM VirtualBox.

## 2026-07-25

- Scheduler made address-space-aware: each task now carries the `AddressSpace` it runs in, and both the timer-tick and voluntary-yield switch paths reload CR3 for the incoming task right before the existing register swap. `spawn` still defaults every task to the kernel's own AddressSpace; a new `spawn_in` picks a specific one. A new self-test spawns one task per AddressSpace, each writing a different pattern to the same virtual address backed by a different physical frame, and confirms both only ever read back their own pattern after several real preemptions interleaved with other running tasks, proving CR3 actually follows the task under real scheduling rather than a single manual switch. Closes the gap flagged in the address-spaces entry below: the scheduler can now genuinely run components in separate AddressSpaces. Doesn't touch capabilities yet, so nothing stops a task from calling kernel functions directly today; that's the next layer. Zero build warnings. Verified on QEMU BIOS+UEFI and confirmed in Oracle VM VirtualBox, identical isolation result with real hardware timer ticks interleaved in. Promoted `main` to `stable`.
- Address spaces added: page tables are now built around an `AddressSpace` handle instead of one implicit global table set. `new_address_space()` builds a fresh one sharing the kernel/HHDM upper half (present, supervisor-only) with a private, zeroed lower half. `map_page`/`unmap_page`/`switch`/a new read-only `is_mapped` check are all methods on it now. The usermode self-test moved into a real second AddressSpace, writing its program in through the target frame's permanent HHDM alias instead of through the not-yet-active user virtual address, which also retires the earlier WRITABLE-then-remap workaround from the ring3 feature (kept in `BUGS.md` as history, noted here as the reason it's obsolete). A new self-test proves two AddressSpaces are actually isolated from each other and that switching CR3 between them and back works. Documented two known gaps rather than fixing them yet: the kernel/HHDM sharing is present-but-supervisor-only, not yet the stricter "structurally unmappable" goal in the kernel README; and the scheduler's context switch still never touches CR3, fine while every task shares the kernel's own AddressSpace, but blocking before multiple components can each run in their own. No teardown/free for an AddressSpace yet, same accepted category of scope cut as the heap's no-coalescing. Zero build warnings. Verified on QEMU BIOS+UEFI and confirmed in Oracle VM VirtualBox, identical serial log including real hardware timer ticks. Promoted `main` to `stable`.
- Ring 3 / user mode added: kernel drops to CPL3 for the first time, via new user GDT selectors, a syscall gate at IDT vector 0x80 (DPL=3, only that one gate), and a `PAGE_USER` fix so the U/S bit actually propagates through every level of the page-table walk, not just the leaf. A hand-written asm program (not compiled Rust; no user-mode runtime exists yet) makes two round-trip `int 0x80` syscalls, then parks for good after the kernel logs and halts on the second one. No process model, no way back into the interrupted kernel flow, no second user task; all deliberate v0.1 scope cuts. Hit and fixed one real bug: the kernel's own copy into the user code page needs WRITABLE set regardless of ring, CR0.WP doesn't check CPL. Zero build warnings. Verified on QEMU BIOS+UEFI and confirmed in Oracle VM VirtualBox (identical two-syscall sequence and halt line). Promoted `main` to `stable`.
- Kernel boot verified in Oracle VM VirtualBox, matching QEMU serial output. Promoted `main` to `stable` (see `BRANCHING.md` merge log).
- Memory bring-up: kernel parses Limine's memory map and logs every region over serial. Physical frame allocator built on top (free-list, HHDM-addressed, self-test on boot). Verified on QEMU BIOS+UEFI and Oracle VM VirtualBox. Promoted `main` to `stable` again (see `BRANCHING.md` merge log).
- GDT/IDT and kernel-owned page tables added (all 32 exception vectors, double-fault IST stack, W^X kernel image mapping, HHDM remap, map/unmap self-tests). Verified on QEMU BIOS+UEFI and now in Oracle VM VirtualBox too, serial logs match exactly. Promoted `main` to `stable`.
- Kernel heap added (free-list first-fit, 1MiB fixed region, backs `extern crate alloc`). Self-test exercises Box and a growing Vec, confirms memory returns on drop. Verified on QEMU BIOS+UEFI and Oracle VM VirtualBox. Promoted `main` to `stable`.
- PIC + PIT timer added (IRQ0 remapped to vector 32, 100Hz). Hardware IRQ0 never reaches the CPU in this dev sandbox's QEMU/TCG despite verified-correct PIC/PIT programming; confirmed via a VirtualBox boot (real hardware virtualization) that this is a sandbox-only limitation, not a kernel bug, since the tick handler fired and the counter advanced normally there. That same VirtualBox run also surfaced a real bug in the self-test's own timeout math (frequency floor instead of ceiling, caused an early false negative on fast hosts); fixed. Boot self-test is timeout-bounded with a software-interrupt fallback so it never hangs in this sandbox. Verified on QEMU BIOS+UEFI and boot-chain-verified through the timer stage in Oracle VM VirtualBox. Promoted `main` to `stable`.
- Scheduler v0.1 added: task struct, hand-written context switch (naked asm), single round-robin queue, timer-tick and voluntary-yield preemption paths. Cooperative two-task self-test proves round-robin switching works independent of whether hardware timer interrupts fire at all. Hit and fixed three real bugs during bring-up: a fabricated stack frame written in the wrong order (crashed with a page fault at rip=0); a self-test task that stopped yielding after finishing (froze the whole round-robin ring); and a boot-order bug that only a VirtualBox run on real hardware exposed, where the first hardware timer tick landed before the scheduler was initialized and panicked on a modulo by zero (this sandbox's QEMU/TCG never delivers a real IRQ0, so it never hit this). Verified on QEMU BIOS+UEFI, zero build warnings, and confirmed in Oracle VM VirtualBox for the boot-order fix specifically (same result, no panic). Promoted `main` to `stable`.
- Added a countdown to the timer self-test's ~2s wait (serial output) and to `smoke-test.sh`'s fixed boot wait (terminal output), so a slow wait doesn't look identical to a hang. Only visible in this sandbox's software-int-fallback path; real hardware finishes the wait too fast to ever reach it.
