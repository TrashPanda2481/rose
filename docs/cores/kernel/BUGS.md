## [FIXED] double fault immediately after CR3 switch to kernel-owned page tables
Date found: 2026-07-25
Date fixed: 2026-07-25
Symptom: booting past "rose: page tables loaded, kernel-owned" never happened; serial log showed vector=8 (double fault) with rip pointing a few instructions after the `mov cr3` in paging::switch_to, then halt.
Cause: paging::build only mapped the HHDM range for MEMMAP_USABLE regions. Limine's default 64KiB boot stack (no StackSizeRequest sent) is allocated out of MEMMAP_BOOTLOADER_RECLAIMABLE memory, and that stack is still in use the instant CR3 changes. First stack access after the switch (a spilled local a few instructions later) had no mapping in the new tables, page-faulted, and the page fault itself couldn't be delivered cleanly (stack still bad), producing a double fault.
Fix: also map MEMMAP_BOOTLOADER_RECLAIMABLE through HHDM alongside MEMMAP_USABLE in paging::build. Does not change what the frame allocator hands out, only what's mapped.
Commit/ref: kernel: page tables

## [FIXED] timer self-test timeout used a frequency floor instead of a ceiling, aborted early on fast hosts
Date found: 2026-07-25
Date fixed: 2026-07-25
Symptom: a VirtualBox boot showed the one-time "first irq0 tick received" log firing and the tick counter reaching 21, proving real hardware IRQ0 delivery works there; despite that, `timer_selftest` still printed "no hardware irq0 within ~2s" and fell back to the software interrupt path, contradicting the ticks that were visibly happening.
Cause: `timer_selftest`'s RDTSC-based timeout computed `cycle_budget = MIN_ASSUMED_HZ * WAIT_SECONDS` using a 500MHz floor, intending to bound the wait to "about 2 seconds." That's backwards: `real_elapsed_seconds = cycle_budget / actual_hz`, so a floor only bounds the wait correctly when the real CPU is slower than the floor. On a real multi-GHz host (as in VirtualBox, running on real host hardware instead of QEMU/TCG emulation), the budget of 1 billion cycles elapsed in a couple hundred milliseconds, not 2 seconds, so the test gave up almost immediately, before the 100Hz timer could reach 50 ticks, and misreported a working timer as absent.
Fix: swapped the constant to `MAX_ASSUMED_HZ = 8_000_000_000` (an assumed ceiling, not floor) so `cycle_budget / actual_hz >= WAIT_SECONDS` holds for any realistic host clock speed. This is a self-test bug only; the underlying PIC/PIT/IDT timer implementation was already correct, as proven by the tick counter advancing on VirtualBox before the fix. Re-verified after the fix with a second VirtualBox boot: self-test now passes clean, `50 ticks elapsed via hardware irq0, 510ms since boot`.
Commit/ref: kernel: timer (PIC + PIT, IRQ0-gated self-test with software-int fallback)

## [FIXED] spawned tasks page-faulted at rip=0 on their first switch-in
Date found: 2026-07-25
Date fixed: 2026-07-25
Symptom: first boot of the scheduler self-test paniced with `EXCEPTION vector=14 (page fault) error_code=0x10 rip=0x0000000000000000 faulting address (cr2)=0x0`, right after the first `yield_now()` call switched away from task 0.
Cause: `spawn()` fabricates a fake saved-context frame on the new task's stack so `context_switch`'s pop sequence resumes into `task_trampoline` instead of a real prior call. The frame values were written with `frame.iter().rev()`, which put `task_trampoline` (meant to be the return address, popped last) at the lowest address (popped first, into r15) and the r15 zero-word at the highest address (meant to be the return address). `context_switch` ended up popping garbage into the callee-saved registers and then `ret`-ing to address 0.
Fix: write the frame top-down in the order it's declared (no reversal), so `task_trampoline` lands at the highest address (last popped, used by `ret`) and each register value lands where its matching `pop` expects it.
Commit/ref: kernel: scheduler (round-robin, context switching)

## [FIXED] scheduler self-test hung after first task finished
Date found: 2026-07-25
Date fixed: 2026-07-25
Symptom: after fixing the frame-layout bug above, boot got past the first switch but then hung indefinitely after `rose: timer self-test`, no further serial output, no panic.
Cause: `task_a`/`task_b` parked in `loop { spin_loop() }` after finishing their 10 iterations, without ever calling `yield_now()` again. Round-robin selection always advances to `(current + 1) % len` regardless of whether the task actually being switched to will ever yield back; once either task parked, control passed to it once and then never rotated again, freezing every other task in the ring, including task 0's own `while TASKS_DONE < 2` wait loop.
Fix: changed both parking loops to `loop { scheduler::yield_now(); }` so a finished task keeps participating in the rotation instead of dead-ending it. Round-robin still has no concept of "done"/skippable tasks; a real scheduler needs one before this class of bug stops being possible by construction, tracked as a known gap for v0.2.
Commit/ref: kernel: scheduler (round-robin, context switching)

## [FIXED] scheduler panic on real hardware: modulo by zero in tick()
Date found: 2026-07-25
Date fixed: 2026-07-25
Symptom: QEMU (BIOS/UEFI, this sandbox) booted clean through the scheduler self-test every time. A VirtualBox boot on real hardware panicked earlier, right after "rose: timer: first irq0 tick received": `panicked at src/scheduler.rs:142:26: attempt to calculate the remainder with a divisor of zero`.
Cause: `idt.rs` calls `scheduler::tick()` unconditionally on every timer IRQ, but `kernel_main` didn't call `scheduler::init()` (which registers task 0) until `scheduler_selftest()`, well after `pic::init()`/`timer::init()` already executed `sti`. In this sandbox's QEMU/TCG, IRQ0 never actually reaches the CPU (see TROUBLESHOOTING.md), so the empty-queue window was never exercised. On VirtualBox, real hardware delivers IRQ0 immediately once IF goes high, so ticks landed on an empty `tasks` Vec; the 5th one reached `tick()`'s round-robin step and computed `(0 + 1) % 0`.
Fix: moved the `scheduler::init()` call to immediately before `pic::init()`, so task 0 is always registered before interrupts are ever enabled; removed the now-duplicate `init()` call from `scheduler_selftest()`. Also added a defensive `if tasks.is_empty() { return }` guard at the top of `tick()` itself, since this path is reachable from a real hardware interrupt whose timing this kernel doesn't control, not just from code that polls something on its own schedule.
Confirmed fixed in Oracle VM VirtualBox: re-ran the fix, no panic, boot chain reaches `rose: scheduler self-test: task_a=10 task_b=10 switches=31` same as QEMU (real hardware ticks completed the 50-tick wait in 510ms).
Commit/ref: kernel: scheduler (round-robin, context switching), boot-order fix

## [FIXED] usermode self-test #PF copying the program into its own code page
Date found: 2026-07-25
Date fixed: 2026-07-25
Symptom: first boot of the usermode self-test got as far as "rose: scheduler self-test" then paniced with `EXCEPTION vector=14 (page fault) error_code=0x3 rip=0xffffffff80005153 faulting address (cr2)=0x0000000000400000`, before ever reaching ring 3.
Cause: the user code page was mapped R+X+U only (no WRITABLE), on the assumption that CPL0 writes bypass page permission checks the same way it bypasses the U/S check when SMAP/SMEP aren't enabled. That's true for U/S; it isn't true for the writable bit. CR0.WP still blocks a supervisor write to a page missing PAGE_WRITABLE regardless of ring. `usermode_selftest`'s own `copy_nonoverlapping` into that page (copying the hand-written program in) faulted immediately, error_code=0x3 decodes to present+write+supervisor, matching exactly.
Fix: map the code page WRITABLE first, do the copy, then call `paging::map_page` again on the same virt+phys with WRITABLE dropped (R+X+U only) before ever entering ring 3. `map_page` just overwrites the leaf PTE, no unmap step needed between the two calls.
Confirmed fixed in Oracle VM VirtualBox: re-ran the fix, same two-syscall sequence and final halt line as QEMU, no fault.
Commit/ref: kernel: user mode (ring 3, syscall gate, usermode self-test)

## [FIXED] real hardware timer preemption during ring-3 self-test reverts CR3 to the kernel AddressSpace
Date found: 2026-08-01
Date fixed: 2026-08-01
Symptom: QEMU (BIOS/UEFI, this sandbox) ran the full ten-step usermode self-test (six CSpace syscalls plus the four new Retype ones) clean every time. A VirtualBox boot on real hardware got through step 9 (retype slot6->slot9, Frame, correctly reports Exhausted) and then faulted on the very next ring-3 instruction: `EXCEPTION vector=14 (page fault) error_code=0x14 rip=0x0000000000400115`, `faulting address (cr2)=0x0000000000400115`, then unrecoverable halt. error_code 0x14 decodes to not-present + user-mode + instruction-fetch. Disassembling the built program confirms 0x400115 is exactly the byte offset of step 10's first instruction (`mov rdi, 6`), the instruction immediately after step 9's `int 0x80` returns; every instruction up to and including that one, in the same single mapped page, had already executed without a fault.
Cause: `usermode_selftest` builds a real second `AddressSpace` (`user_as`) and switches CR3 into it by calling `user_as.switch()` directly, then `enter_user_mode`, entirely bypassing the scheduler. Task 0's own `Task.address_space` field, set at task creation, is still `paging::kernel_address_space()`, since nothing updates it to `user_as` when the manual switch happens; the scheduler has no idea CR3 changed out from under it. `scheduler::tick()`, called unconditionally from the timer IRQ handler with real interrupts enabled (rflags=0x202 in the ring-3 program), reloads CR3 to whatever `Task.address_space` the round-robin's next task carries, unconditionally, every timeslice (5 ticks, 50ms at 100Hz). Round-robin trip: task 0 -> task_a/task_b (both spawned via plain `spawn()`, `address_space` = kernel's own) -> eventually back to task 0, at which point `tick()` reloads CR3 from task 0's *stale* field, i.e. back to the kernel's own AddressSpace, discarding `user_as` entirely. Execution resumes at the saved rip (mid ring-3 program) under the wrong page tables, where `CODE_VADDR` (0x400000) was never mapped, faulting on the very next instruction fetch. This never showed up before because IRQ0 never reaches the CPU in this sandbox's QEMU/TCG (see TROUBLESHOOTING.md), so `tick()` never actually preempts during the ring-3 program there regardless of how long it runs; and the six-step CSpace-only version of the program, the only one run in VirtualBox before this feature, apparently finished inside a single 50ms timeslice, so this never got exercised on real hardware either. Adding the four Retype steps (more instructions, plus heap-touching CSpace/Untyped work and a serial log line per step) was enough to push real elapsed time on VirtualBox's real UART/hardware past the first 50ms boundary, exposing a gap that has been latent since the ring-3 self-test was first written to run with interrupts enabled while not being a real scheduler-tracked task.
Fix: implemented candidate (a). Added `scheduler::set_current_address_space(new_as)`, which updates the current task's `Task.address_space` field and reloads CR3 into it in one step, cli/sti-bracketed so no tick can land between the two and see a mismatched pair. `usermode_selftest` now calls this instead of `user_as.switch()` directly before dropping to ring 3, so task 0's bookkeeping and its actual CR3 stay in sync; the next real preemption that cycles back to task 0 reloads `user_as`, not a stale kernel AddressSpace. Builds with zero warnings, QEMU BIOS and UEFI both still run the full ten-step self-test clean. Does not touch candidates (b) or (c), and does not change the interrupt-frame/stack-sharing plumbing that lets real hardware preemption resume a task at all (already proven by the task_c/task_d AddressSpace-under-preemption self-test). QEMU/TCG in this sandbox never delivers real IRQ0, so this fix could not be exercised for real preemption here. Confirmed in Oracle VM VirtualBox: full ten-step sequence now passes clean end to end, step 10 (`retype slot6->slot10 Thread ... ok`) runs, `untyped syscall self-test: sequence complete, overall confirmed`, `usermode self-test: full boot sequence confirmed`; real hardware timer ticks interleaved throughout (`50 ticks elapsed via hardware irq0, 510ms since boot`), no fault.
Commit/ref: kernel: Untyped/Retype v0.1 (surfaced the gap, did not introduce it); 520c5a1 fix(kernel): sync task 0 address_space on manual switch before ring 3 (the fix)

## [FIXED] Configure-spawned second task page-faults on its first instruction, AddressSpace slot9 is not the same address space its code was mapped into
Date found: 2026-08-08
Date fixed: 2026-08-08
Symptom: Oracle VM VirtualBox ran PCI enumeration and the full 13-step usermode self-test clean, all the way through `usermode self-test: full boot sequence confirmed`. Immediately after that line, the kernel faults: `EXCEPTION vector=14 (page fault) error_code=0x14 rip=0x0000000000800000`, `faulting address (cr2)=0x0000000000800000`, then unrecoverable halt. Never seen in this sandbox's QEMU/TCG runs, since IRQ0 there doesn't reliably preempt task 0 into the newly Configured task within the smoke-test's short window (see TROUBLESHOOTING.md); VirtualBox's real hardware timer does, so this is the first time that task has ever actually been switched into.
Cause: `usermode_selftest` (`main.rs`) maps `CODE2_VADDR`/`STACK2_VADDR` (0x800000/0xa00000, program2's code and stack) into `user_as`, the same AddressSpace the calling task itself runs in. Step 13's Configure syscall, however, targets AddressSpace slot9, and a comment at the mapping site claims slot9 "is user_as itself (retyped in step 9)". That's incorrect: `untyped::retype`'s `ObjectType::AddressSpace` arm unconditionally calls `paging::new_address_space()`, which allocates a brand-new PML4 sharing only the standard kernel/HHDM upper half, empty lower half, no relation to `user_as` at all. Slot9 is a genuinely separate, blank address space. Configure schedules the new task against that blank AddressSpace, so once a real preemption actually lands there, the very first ring-3 instruction fetch at 0x800000 finds nothing mapped and faults; error_code=0x14 decodes to not-present + user + instruction-fetch, and both cr2 and rip land exactly on the entry address, consistent with this cause. This is a pre-existing gap in the Configure feature (2026-08-01), first exposed now because this is the first VirtualBox run to reach a real preemption past Configure; unrelated to this session's PCI enumeration work, which ran and completed correctly beforehand.
Fix: option (b) from the two candidates: added a real, generic Map syscall (`SYS_FRAME_MAP = 0x1006`, `dispatch_frame_map` in `syscall.rs`) that lets a task with a Frame cap (MAP right) and an AddressSpace cap (MAP right) map that frame at a caller-given virtual address, using `paging::AddressSpace::from_raw()` (already existed, contrary to an earlier assumption this session that it needed to be built) plus `AddressSpace::map_page()`. Wired into `idt.rs`'s syscall dispatch chain alongside CSpace/Retype/Configure. The ring-3 self-test program now issues two Map syscalls between steps 9 and (old) 10: one mapping the already-retyped-but-previously-unused slot7 Frame into slot9 at STACK2_VADDR with WRITABLE|NO_EXECUTE, one mapping a newly pre-populated slot13 Frame (granted as a root cap by `main.rs`, containing program2's real instruction bytes copied at ring-0 setup time, same boot-handoff pattern as slot1/slot6) into slot9 at CODE2_VADDR with no WRITABLE flag. This closes the actual gap: slot9 now has real mappings at both addresses before Configure ever schedules a task against it. Turned out smaller than originally scoped when this fix was approved: no Untyped pool growth to 5 frames was needed (contrary to an earlier estimate this session), since the stack page could reuse the already-existing step-7 Frame instead of retyping a new one. Confirmed passing in this sandbox's QEMU (BIOS `smoke-test.sh` and UEFI `run-uefi.sh`), zero warnings, all self-test steps including both new Map steps pass, no page fault; NOT yet re-confirmed in VirtualBox on real hardware, where the original symptom was actually observed. Program2's own liveness syscall still didn't fire in this sandbox's QEMU/TCG run, consistent with the pre-existing IRQ0-preemption limitation noted above and in TROUBLESHOOTING.md, not a new issue.
Commit/ref: kernel: Frame-Map syscall (SYS_FRAME_MAP), fixes Configure page-fault
Update 2026-08-08: re-confirmed in VirtualBox. Fresh serial log shows no fault at rip=cr2=0x0000000000800000; program2 now executes its first instructions and makes its own liveness syscall (`syscall #3, rax=0x1`) for the first time in any run, QEMU or VirtualBox. Original symptom is gone. A different, new fault immediately follows; see the new open entry below, this fix is not reverted or in question, the two are distinct.

## [FIXED] second page fault immediately after program2's first syscall returns, same code page, next instruction
Date found: 2026-08-08
Date fixed: 2026-08-08
Symptom: Same VirtualBox run that confirmed the fix above. After `rose: usermode self-test: syscall #3 from ring 3, rax=0x1` (program2's own int 0x80, logged by the generic/legacy syscall path), the kernel faults on the very next line: `EXCEPTION vector=14 (page fault) error_code=0x14 rip=0x0000000000800009`, `faulting address (cr2)=0x0000000000800009`, then unrecoverable halt. error_code=0x14 decodes the same way as the original bug (not-present, instruction fetch, user mode), but at a different address, and only after real execution already happened on that same page. Byte-counted program2's own code (`usermode.rs` `user_program2_start`..`user_program2_end`): `mov rax, 1` is 7 bytes, `int 0x80` is 2 bytes, total 9; offset 9 is exactly where the following `jmp 2b` starts. So the fault is on the first instruction fetch after the kernel's iretq hands control back to ring 3 following program2's syscall, not on program2's own entry point, and not mid-instruction.
Cause: Not yet confirmed with runtime instrumentation, but narrowed considerably by further code reading. Ruled out: a stale/wrong AddressSpace handle at Configure time; `dispatch_configure` in `syscall.rs` resolves the AddressSpace cap via `paging::AddressSpace::from_raw(as_cap.object_ref.0)`, the same reconstruction Frame-Map uses against the same slot9 physical PML4, so the Task's stored `address_space` field is correct. Ruled out: a nested interrupt landing inside the int 0x80 handler itself; vector 0x80's IDT gate is a genuine interrupt gate (`Entry::set_user`, `type_attr = 0xEE` -- DPL=3, type 0xE; corrected 2026-08-09 from an earlier draft of this entry that cited 0x8E, the DPL=0 constant used by every other gate, which would `#GP` a ring-3 caller), so IF is cleared for the whole handler. Ruled out (corrected from an earlier draft of this entry): that no real multi-task context switch happened before Configure. That assumption was wrong; `scheduler_selftest`'s task_a/task_b/task_c/task_d never leave the round-robin (a spawned task's `task_trampoline` drops into `hlt; jmp 2b` forever when its function returns), so real switches were already happening throughout the whole run. They just never touch the mechanism below: those four run entirely in ring 0, and the CPU only loads TSS.RSP0 on a ring3->ring0 transition, a same-ring interrupt keeps using whatever stack was already active. Also confirmed program1 itself has been ring-3 resident since before step 1 (`enter_user_mode` is one-way, called once), and its own int 0x80 syscalls for steps 1-13 already went through the shared RSP0 buffer and survived many real preemptions solo, so ring-3 residency by itself is not sufficient to cause this. Leading candidate: `gdt::set_kernel_stack` (TSS.RSP0) is called exactly once in `main.rs`, a single global ring0 stack shared by every ring3->ring0 transition, never updated per task. A task preempted mid-interrupt (via `scheduler::tick()`'s `context_switch`, a raw stack-pointer swap, not an iretq) has its whole resume chain, including the hardware-pushed exception frame, parked wherever RSP happened to be; nothing reserves that memory. Configure is the point where a *second* ring-3-resident task first exists and starts alternating with program1 through that same single buffer, the first time two independent ring3->ring0 transitions can collide over it, which lines up exactly with when the fault first appears. Still unconfirmed: proving byte-for-byte that this specific collision produces the exact observed rip=0x800009 would need runtime instrumentation or a fix attempt; not verifiable from source alone since it depends on compiler-chosen stack frame sizes.
Fix: gave every task its own private ring0 entry stack instead of the single global one. Added `kernel_stack_top: u64` to `scheduler.rs`'s `Task` struct, populated at all three creation sites (`init()` for task 0, `spawn_in()`, `spawn_user()`) from the same stack-top value each already computes for its own frame. Added `scheduler::set_current_kernel_stack()`, mirroring the existing `set_current_address_space()` (same cli/sti bracket, same reasoning: update the Task field and apply to the TSS immediately, atomically, so a real tick can't land in between and see a mismatched pair). `main.rs`'s old one-time raw `gdt::set_kernel_stack(scratch_top)` call is replaced with a call through this new function, so task 0's own field gets recorded instead of just applying the value once and forgetting it. `tick()` and `yield_now()` now read the incoming task's `kernel_stack_top` and call `gdt::set_kernel_stack()` on it right alongside the existing per-task CR3 reload, unconditionally, before `context_switch`. No changes needed to `context_switch` itself, AddressSpace/CR3 handling, `common_stub`, or syscall dispatch. Every ring-3-resident task now traps through its own dedicated buffer, so the two-task collision this bug's cause section describes is no longer structurally possible. Confirmed in Oracle VM VirtualBox: fresh serial log shows `rose: usermode self-test: syscall #3 from ring 3, rax=0x1` as the last line, no `EXCEPTION` line following it. Program2's own trampoline parks in its infinite `jmp 2b` loop after this, which prints nothing further, so a clean log ending right there, with no fault, is the expected success shape, not a truncation. All 15 self-test steps preceding it (cspace, untyped, frame-map, configure) show the same expected results as the QEMU run. This is the first confirmed-working run of two ring-3-resident tasks coexisting under real hardware preemption.
Commit/ref: 620903e (cause correction), 2e9f782 (fix)

## [FIXED] SYS_FRAME_MAP: ring-3 privilege escalation / arbitrary physical memory corruption
Date found: 2026-08-09
Date fixed: 2026-08-09
Symptom: Found via code audit (5 parallel independent review passes, 2 of which converged on this from different angles), not a runtime symptom -- no self-test exercises the vulnerable path, since every existing Frame-Map call uses a hardcoded low vaddr (STACK2_VADDR/CODE2_VADDR, 0xa00000/0x800000) against a non-kernel AddressSpace (slot9).
Cause: three independent, compounding gaps in `dispatch_frame_map` (syscall.rs) and its call into `paging::map_page`. (1) No check that the caller-supplied `vaddr` stays out of the PML4 range every AddressSpace shares BY PHYSICAL REFERENCE with the kernel's own tables (`new_address_space` copies PML4 entries 256..511 by value, not a deep copy) -- a task holding only the default rights `retype` already grants (any Frame cap, any AddressSpace cap) could map an attacker-chosen frame directly over kernel `.text`, with PAGE_USER set and NX clear, and the next kernel instruction fetch through there executes it at ring 0. (2) `paging::next_level` never checked `PAGE_HUGE` on a present PD entry before treating its address bits as a pointer to a further table; most of HHDM is 2MiB-huge-mapped, so a vaddr landing there made the kernel reinterpret live RAM as a page table and write an attacker-chosen PTE into it -- memory corruption independent of (1). (3) Neither Frame-Map nor Configure checked whether the resolved AddressSpace cap *was* the kernel's own; task 0's legitimate boot-handoff cap over `kernel_address_space()` alone satisfied every existing check, so the most direct exploit path didn't even need the upper-half-sharing trick from (1). Concrete sequence (pre-fix): `int 0x80`, `rax=SYS_FRAME_MAP`, `rdi=<any Frame cptr>`, `rsi=<any AddressSpace cptr with MAP>`, `rdx=0xffff800000000000`, `r10=MAP_FLAG_WRITABLE`.
Fix: three independent closing mechanisms, kept all three rather than relying on just one (defense in depth). Added `paging::is_shared_vaddr(virt)` (checks the vaddr's PML4 index against the same `SHARED_PML4_RANGE` constant `new_address_space` already uses) and reject in `dispatch_frame_map` before ever reaching `map_page`. Added `AddressSpace::is_kernel()` and reject in both `dispatch_frame_map` and `dispatch_configure` when the resolved AddressSpace cap is the kernel's own -- closes the private-half gap (1) doesn't cover, since even a vaddr outside the shared range would still target the kernel's live PML4. Added an `assert!` on `PAGE_HUGE` in `next_level` itself as a structural second line of defense: should be unreachable given (1)/(2) above, and if it's ever hit anyway, halts loudly instead of corrupting memory silently. Verified: `cargo check`/`cargo build --release` clean, zero warnings; confirmed by hand that the existing self-test's Frame-Map/Configure calls (vaddrs 0x800000/0xa00000, AddressSpace slot9, a genuinely fresh Retype'd AS) don't trip any of the three new checks. NOT yet booted -- no QEMU available in the environment this fix was written in; needs a real smoke-test run (BIOS + UEFI QEMU, then VirtualBox per the usual promotion checklist) before this is trusted.
Commit/ref: 458fe52

## [FIXED] SYS_FRAME_MAP: W^X bypassable (writable + executable mapping in one call)
Date found: 2026-08-09
Date fixed: 2026-08-09
Symptom: Found via code audit, not a runtime symptom. No self-test currently requests this combination (the stack mapping asks for WRITABLE|NO_EXECUTE, the code mapping asks for neither).
Cause: `dispatch_frame_map` built its PTE flags from two independent caller-supplied bits (MAP_FLAG_WRITABLE, MAP_FLAG_NO_EXECUTE) with no rule tying them together. A task could request MAP_FLAG_WRITABLE alone, producing a page that's simultaneously writable and executable -- undermining the W^X discipline `paging::build()`'s own kernel-image mapping documents itself as enforcing "from the very first kernel-owned page table."
Fix: `dispatch_frame_map` now sets PAGE_NO_EXECUTE whenever MAP_FLAG_WRITABLE is requested, regardless of whether the caller separately asked for MAP_FLAG_NO_EXECUTE. Verified: existing self-test's two Frame-Map calls unaffected (stack mapping already requested NO_EXECUTE explicitly; code mapping never requests WRITABLE).
Commit/ref: 458fe52

## [FIXED] Missing cli guard on SCHEDULER lock in spawn/spawn_in/spawn_user/with_current_cspace: deadlock under real preemption
Date found: 2026-08-09
Date fixed: 2026-08-09
Symptom: Found via code audit, unconfirmed at runtime -- this sandbox's QEMU/TCG never delivers real IRQ0 (see TROUBLESHOOTING.md), so the window this bug depends on can't be hit here; would need a VirtualBox real-hardware run, with the critical section artificially widened or many repeated boots, to actually trigger.
Cause: `scheduler::spawn_in`/`spawn_user` (SCHEDULER.lock() around the tasks.push) and `scheduler::with_current_cspace` (SCHEDULER.lock() around the current-task lookup) all acquired the SCHEDULER SpinLock with no cli guard, unlike `set_current_address_space`/`set_current_kernel_stack`, which do. `spawn_in` is called from `main.rs`'s `scheduled_address_space_selftest`, and `with_current_cspace` from both `main.rs`'s boot-handoff `grant_root` calls and every syscall dispatch function -- all after `pic::init()`/`timer::init()` have already enabled interrupts. A real timer tick landing inside any of these critical sections calls `tick()`, which tries to re-lock the same non-reentrant SpinLock from inside an interrupt-gate ISR (IF stuck at 0) and spins forever -- a permanent hang, single core, nothing else could ever release it. `spawn_in`'s own doc comment claimed this was "only safe to call during boot setup, before any of these tasks can actually be preempted," which was already false by the time `scheduled_address_space_selftest` started calling it post-`pic::init()`.
Fix: added `scheduler::save_flags_and_cli()`/`restore_flags()`, a proper save-and-restore pair (reads RFLAGS, clears IF, later `sti`s only if IF was actually set) rather than a blind cli/sti. A blind pair (fine for `set_current_address_space`/`set_current_kernel_stack`, each confirmed to have exactly one caller always at IF=1) would be actively wrong here: `with_current_cspace`/`spawn_user` are also called from *inside* the vector-0x80 syscall interrupt handler itself (a genuine interrupt gate, IF already 0 for the whole handler), where a blind `sti` would incorrectly re-enable interrupts mid-handler before its own `iretq` restores the real saved state. Applied the same helper to `spawn_in`, `spawn_user`, and `with_current_cspace`; corrected `spawn_in`'s now-false doc comment. `scheduler::init()` (task 0's own registration, confirmed to run before `pic::init()`'s `sti`) deliberately left untouched -- interrupts genuinely aren't enabled yet there, so neither cli nor sti apply.

## [FIXED] Configure commits (consumes) a caller's CSpace object before verifying the target thread is configurable
Date found: 2026-08-09
Date fixed: 2026-08-09
Symptom: Found via code audit, not exercised by the current self-test (usermode.rs's one Configure call always passes cspace_cptr=0/None, so `take_cspace` is never reached either way).
Cause: `dispatch_configure` called the irreversible `untyped::take_cspace` (removes the entry from CSPACE_OBJECTS on success, no way back) before `thread::configure`'s own `peek_thread_unconfigured` check, which can still fail (AlreadyConfigured/InvalidThread) after `take_cspace` already ran. Re-running Configure against an already-configured Thread cptr, together with a real (non-zero) CSpace cptr, silently destroyed the caller's CSpace object even though the syscall reported failure -- the exact "commit before verify" pattern this kernel's own design principle (README.md, "verify before commit") warns against, directly contradicting thread.rs's own doc comment claiming the peek happens "before doing anything else."
Fix: moved a `untyped::peek_thread_unconfigured` call into `dispatch_configure`'s own closure, right after the Thread cap resolves and before the CSpace-cptr branch that calls `take_cspace`. The equivalent check inside `thread::configure` (right before `claim_thread`) is left in place as the authoritative, closest-to-the-actual-commit guard -- this is a second, earlier gate, not a replacement.

## [FIXED] Untyped Retype ignores capability rights on the Untyped cap itself
Date found: 2026-08-09
Date fixed: 2026-08-09
Symptom: Found via code audit, not exercised by the current self-test (the root Untyped cap is always granted `full_rights` = READ|WRITE|MAP).
Cause: `dispatch_untyped` checked only `object_type == ObjectType::Untyped` on the Untyped capability argument, never a rights bit -- unlike Configure (checks GRANT/MAP on all three of its cap args) and Frame-Map (checks MAP/WRITE). Minting an Untyped cap down to `Rights::NONE`, the standard way to hand a narrowed-confinement view to a less-trusted delegate, had no effect on Retype: the "rights bound what you can do with a cap" invariant held for every other object type but this one. Not yet exploitable across a trust boundary in v0.1 (no cross-CSpace cap delegation exists -- `move_slot` is same-CSpace only, IPC unimplemented), but cheap to close now, before IPC lands and makes it a live confinement bypass.
Fix: `dispatch_untyped` now also requires `Rights::WRITE` on the Untyped cap, matching the pattern every other typed cap argument in this file follows. WRITE was picked as the gating right; matches the boot-handoff grant (`full_rights`), so no existing caller's behavior changes.
