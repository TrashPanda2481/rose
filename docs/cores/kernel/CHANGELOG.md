# Changelog: kernel core

Date, change, why. Newest first.

## 2026-08-09

- Security audit fixes, five findings from a 5-agent parallel audit of `kernel/src` (`kernel/src/paging.rs`, `kernel/src/syscall.rs`, `kernel/src/scheduler.rs`): closes gaps in the Frame-Map and Configure syscalls that let a ring-3 task escalate privilege against its own kernel, plus a scheduler lock ordering issue that could deadlock a single core. Full symptom/cause/fix writeups in `BUGS.md`, one entry per finding. Verified on QEMU BIOS and UEFI, zero build warnings, all self-test steps pass clean, identical result both boot paths. Confirmed in Oracle VM VirtualBox: full self-test sequence passes identically, including 50 real hardware timer ticks during boot with no hang, consistent with the scheduler locking fix but not a targeted stress test of its exact race window (see BUGS.md for the caveat on that specific finding). Promoted to `stable` (a683694).
  - CRITICAL: `dispatch_frame_map` (`syscall.rs`) let a caller map any frame into the kernel's own shared higher-half address range (`paging::is_shared_vaddr` gate added) and, separately, into an AddressSpace flagged as kernel-owned (`AddressSpace::is_kernel()` gate added); either alone was a path to writing kernel memory from ring 3.
  - HIGH: same syscall accepted `MAP_FLAG_WRITABLE` without forcing `PAGE_NO_EXECUTE`, so a mapped frame could be both writable and executable at once (W^X violation); now any writable mapping is unconditionally also no-execute.
  - HIGH: `next_level()` (`paging.rs`) treated a present page-table entry as a pointer to a next-level table without checking the huge-page bit first; a malicious or malformed huge-page entry could be walked as if it were a table, corrupting the walk. Added an explicit assert that the huge bit is clear before treating an entry as a table pointer.
  - MEDIUM: `dispatch_configure` (`syscall.rs`) committed the new thread/CSpace/AddressSpace wiring before confirming the target thread was actually unconfigured, violating this doc's own "verify before commit" principle (logged above, 2026-08-08); reordered so `untyped::peek_thread_unconfigured` runs first and nothing is written until it passes. Also added a check that the target AddressSpace isn't the kernel's own.
  - MEDIUM: `dispatch_untyped` (`syscall.rs`) didn't check the WRITE right on the Untyped cap before allowing Retype, so a read-only Untyped cap could still be used to carve out new objects; added the missing `Rights::WRITE` check.
  - MEDIUM: `tick()`'s scheduler lock (`scheduler.rs`) could be held across a window where a timer IRQ lands and re-enters the same non-reentrant lock, spinning forever on a single core. New `save_flags_and_cli()`/`restore_flags()` helpers bracket the critical sections in `spawn_in`, `spawn_user`, and `with_current_cspace` with a proper save-then-restore instead of a blind `cli`/`sti`, since these functions are called from both interrupt context (IF already 0) and normal context (IF=1).

- Endpoint IPC v0.1 increment 1 (`kernel/src/endpoint.rs`, new; wired into `kernel/src/untyped.rs`'s Retype, `kernel/src/syscall.rs` (`SYS_ENDPOINT_SEND`=0x1007/`SYS_ENDPOINT_RECEIVE`=0x1008), `kernel/src/idt.rs`'s dispatch chain, `kernel/src/usermode.rs`'s self-test): Endpoint object plus blocking Send/Receive only, no Call yet. `Message{label: u32, data0: u64, data1: u64}` is a two-word subset of the fuller struct in `docs/cores/kernel/README.md`'s IPC section (see that doc's own Update note); this increment's smaller shape is what a self-test can exercise end to end now, not a spec change. Delivery is rendezvous-style: whichever side (sender or receiver) arrives first parks itself as a `Waiter` on the `EndpointObject`; the second arrival finds that Waiter directly and delivers into it (or reads out of it) in place. `send`/`receive` both capture `scheduler::current_index()` before ever taking the `ENDPOINT_OBJECTS` lock, and drop that lock before calling `scheduler::block_current_and_switch()`/`scheduler::wake()`, so the two locks stay strictly sequential, never nested. `untyped::retype`'s new `ObjectType::Endpoint` arm registers an `EndpointObject`; a new `untyped::grant_into_cspace` helper lets `main.rs` grant a capability into an arbitrary CSpace slot directly, used to hand the self-test's second task a RECEIVE-only cap without a syscall round-trip. Self-test: the first task (program1) sends `{label:0x1234, data0:0xdead, data1:0xbeef}` and blocks; the second task (program2) receives it and logs the delivered fields. Zero build warnings.
  Receive-side confirmed on QEMU BIOS and UEFI: the second task's Receive call correctly finds the first task's parked Waiter and logs the exact delivered label/data0/data1. Send-side resume (the first task waking back up, and the self-test's own final aggregate report) could not be observed in this sandbox: it depends on a real timer tick landing on the second task while it spins in its post-Receive loop, since `wake()` only clears the woken task's `blocked` flag and relies on a future `tick()`/`yield_now()` round-robin pass to actually switch back to it (no forced immediate switch, by design, consistent with existing scheduler semantics elsewhere in this file). This sandbox's QEMU/TCG never delivers a real hardware IRQ0 (already documented in `TROUBLESHOOTING.md`); confirmed again here by finding the timer self-test's own `no hardware irq0 within ~2s` line in both the smoke-test log and a fresh 22-second manual BIOS run, and again in a fresh UEFI run, all three truncating at the identical point (right after the Receive self-test's own log line). Since `scheduler::tick()` is only ever called from the real IRQ0 vector in `idt.rs`, it never runs in any of these runs, so the first task can never be resumed here regardless of wait time. This is the same pre-existing, already-documented sandbox limitation surfaced by earlier features (see this file's CR3/AddressSpace entries above), not a new bug introduced by this feature; no scheduler or IPC code change was made or is believed to be needed. Confirmed in Oracle VM VirtualBox: fresh serial log shows real hardware timer ticks (`50 ticks elapsed via hardware irq0, 510ms since boot`) interleaved throughout, the Endpoint Send self-test step passing (`endpoint send syscall self-test: step 1 send slot16 ... result=0x0 ok`, `sequence complete, overall confirmed`), and ends with `usermode self-test: full boot sequence confirmed`. Confirms the round-trip and scheduler/IPC design work correctly under real preemption; the QEMU/TCG truncation above was purely the pre-existing sandbox limitation, not a defect in this feature.

## 2026-08-08

- Per-task kernel entry stacks (`kernel/src/scheduler.rs`, `main.rs`): fixes the open page-fault bug logged below, caused by every task sharing one single global `TSS.RSP0` for every ring3->ring0 trap. Confirmed via code reading that the fault only became possible once Configure created a second ring-3-resident task to alternate with program1 through that one shared buffer; program1 alone had already survived many real preemptions through it without corruption. New `kernel_stack_top: u64` field on `Task`, populated at all three creation sites (`init()`, `spawn_in()`, `spawn_user()`) from the same stack-top value each already computes. New `scheduler::set_current_kernel_stack()`, mirroring the existing `set_current_address_space()` (same cli/sti-bracketed update-then-apply shape); `main.rs`'s old one-time raw `gdt::set_kernel_stack()` boot call goes through this instead, so task 0's own field is recorded, not just applied once and forgotten. `tick()`/`yield_now()` now reload `TSS.RSP0` from the incoming task's own field, unconditionally, right alongside the existing per-task CR3 reload, before `context_switch`. Every ring-3-resident task now traps through its own dedicated stack, so the collision this bug depended on is no longer structurally possible. Zero build warnings. Verified on QEMU BIOS and UEFI, all self-test steps pass clean. Confirmed in Oracle VM VirtualBox: fresh serial log ends cleanly at `syscall #3 from ring 3, rax=0x1` with no `EXCEPTION` line following, the expected shape once program2 parks in its infinite loop; first confirmed-working run of two ring-3-resident tasks coexisting under real hardware preemption. Closes the bug logged below (now `[FIXED]` in `BUGS.md`). Promoted to `stable` together with the PCI enumeration and Frame-Map entries below.
- Frame-Map syscall (`kernel/src/syscall.rs`, new `SYS_FRAME_MAP = 0x1006`/`MapError`/`dispatch_frame_map`; wired into `idt.rs`'s dispatch chain and `usermode.rs`'s ring-3 self-test): fixes the Configure page-fault bug logged below and in `BUGS.md`. Lets a task holding a Frame cap (MAP right) and an AddressSpace cap (MAP right) map that frame at a caller-given virtual address with caller-chosen flags (`MAP_FLAG_WRITABLE`/`MAP_FLAG_NO_EXECUTE`, a small clean bitfield rather than leaking `paging.rs`'s raw PTE bits across the syscall boundary), via `paging::AddressSpace::from_raw()` (already existed, contrary to an earlier assumption this session that it needed to be built) plus `AddressSpace::map_page()`. Own error space (`MapError`: InvalidFrame/InvalidAddressSpace/Misaligned, codes 1-3, +30 offset to avoid colliding with CSpaceError/UntypedError/ConfigureError's own bands). The ring-3 self-test program's fixed sequence grows two steps (now 15 total, inserted between the old steps 9 and 10): one Map call reusing the already-retyped-but-previously-unused slot7 Frame into slot9 at 0xa00000 (STACK2_VADDR) with WRITABLE|NO_EXECUTE, one Map call using a newly pre-populated slot13 Frame (granted as a root cap by `main.rs`, containing program2's real instruction bytes copied at ring-0 setup time, same boot-handoff pattern as slot1/slot6) into slot9 at 0x800000 (CODE2_VADDR) with no WRITABLE flag. `main.rs` no longer maps CODE2_VADDR/STACK2_VADDR into `user_as` at all; those addresses only exist in slot9 now, reached through the new syscall, closing the actual gap (slot9 was a genuinely separate, blank AddressSpace from `user_as`, not the same one as a stale comment claimed). Turned out smaller than originally scoped when approved: no Untyped pool growth to 5 frames needed, the stack page reuses the existing step-7 Frame instead of retyping a new one. Zero build warnings. Verified on QEMU BIOS (`smoke-test.sh`) and UEFI (`run-uefi.sh`): all 15 self-test steps pass including both new Map steps, ending in `usermode self-test: full boot sequence confirmed`, no page fault. Confirmed in Oracle VM VirtualBox by the follow-up entry above; promoted to `stable`.
- Design principle documented, verify before commit (`docs/cores/kernel/README.md`): writes down the standing rule already implicit in Configure's `peek_thread_unconfigured`/`claim_thread` pattern, nothing acts on unconfirmed information, every commit gets a read-only check first. Not a code change on its own; the point is giving future syscalls and hardware-facing code something explicit to be held against instead of re-deriving the discipline from scratch each time.
- PCI enumeration v0.1 (`kernel/src/pci.rs`, new; wired into `main.rs`): first tier 1 hardware detection feature, and the first code to touch a device bus at all. Reads config space through the legacy mechanism #1 I/O ports (0xCF8 CONFIG_ADDRESS, 0xCFC CONFIG_DATA), the one access method every PC-compatible x86 system has supported since the original PCI spec; no ACPI/MCFG parsing needed first, since that doesn't exist in this kernel yet either. `enumerate(on_device)` walks all 256 buses x 32 devices x 8 functions, no shortcuts: it reads only the vendor id first (offset 0x00), and only reads the rest of a slot's config space (device id, revision id, prog-if, subclass, class code, offset 0x08) once a vendor id other than the absent-sentinel 0xFFFF confirms something is actually there, the same peek-then-commit shape the new design principle above describes, applied to hardware instead of a capability. Deliberately not done in v0.1: no multi-function header-type shortcut (every function on every device gets probed the same way regardless of what was found on any other slot, since nothing about the bus topology is trusted ahead of time), no PCIe extended config space, no capability list walking, and no write ever reaches a device, config space reads only. New `main.rs` self-test (`pci_selftest`) calls `enumerate` and logs one line per function found (`rose: pci: bus:device.function vendor=... device=... class=... subclass=... progif=... rev=...`), plus a final count; no expected-device list to assert against on purpose, discovery is the point. `mod pci;` added alphabetically between `paging` and `pic`; `pci_selftest` runs after `cspace_selftest`, before the diverging `usermode_selftest` tail call. Zero build warnings. Verified on QEMU BIOS and UEFI: identical six-device log both times, exactly QEMU's own standard i440FX chipset devices (host bridge, PIIX3 ISA bridge, PIIX3 IDE, PIIX4 ACPI/PM, Bochs VGA, e1000 NIC), all correctly read via class/subclass/prog-if with no driver involved.
- Run in Oracle VM VirtualBox: PCI enumeration itself passed clean, finding 10 real devices with correct vendor/device/class/subclass/prog-if fields, including several never seen in QEMU (an AMD PCnet NIC at 1022:2000, a VirtualBox VGA adapter at 80ee:beef, a VirtualBox Guest Additions device at 80ee:cafe, and USB OHCI/EHCI controllers), a good cross-check that the code reads real config space rather than anything QEMU-specific. Immediately after, the kernel faulted: `EXCEPTION vector=14 (page fault) error_code=0x14 rip=0x0000000000800000`, unrecoverable halt. Not a PCI bug; this is a pre-existing gap in the Configure feature (2026-08-01), first exposed now because this is the first VirtualBox run to reach a real hardware timer preemption into the Configure-spawned second task. Logged as an open bug, see `BUGS.md`, since fixed and merged to `stable` above.

## 2026-08-01

- Configure syscall (`kernel/src/thread.rs`, new; plus changes in `abi/src/lib.rs`/`paging.rs`/`untyped.rs`/`scheduler.rs`/`syscall.rs`/`idt.rs`/`usermode.rs`/`main.rs`): the first syscall that turns a retyped-but-inert Thread object into a real, running ring-3 task, closing the gap the Retype entry below left open (a Thread cap existed but nothing could ever schedule it). `ThreadObject` (`untyped.rs`) grows from an empty placeholder to `{ task_index: Option<usize> }`; new `peek_thread_unconfigured`/`claim_thread` check-then-set the mapping under the same lock `THREAD_OBJECTS` already used, and a new `take_cspace` one-way-consumes a retyped CSpace cap out of `CSPACE_OBJECTS` so Configure can hand it off instead of copying it. `scheduler.rs` gained `spawn_user(entry, user_stack_top, address_space, cspace)`, which fabricates a fake saved-context frame the same way `spawn`/`spawn_in` already do, but resumes into a new naked `user_task_trampoline` that replicates `enter_user_mode`'s exact iretq setup instead of jumping into kernel Rust code; `Task.cspace` changed from `CSpace` to `Box<CSpace>` to make handing one off to a specific new task cheap (move a pointer, not the 64-slot table). `thread::configure(thread_id, address_space, cspace, entry, stack_top)` ties it together: peeks the thread is unconfigured, defaults to a fresh CSpace when the caller passes none, calls `spawn_user`, then claims the thread against the resulting task index. `syscall.rs`'s `dispatch_configure` resolves all three capability arguments (Thread+GRANT, AddressSpace+MAP, CSpace+GRANT or none) inside one `with_current_cspace` closure, then calls `thread::configure` after that closure returns; doing it in that order matters, `thread::configure` reaches into the scheduler through `spawn_user`, and `with_current_cspace` already holds the scheduler lock for its own duration; calling it from inside would self-deadlock. New `SYS_THREAD_CONFIGURE` (0x1005), fifth syscall argument added (`idt.rs` now also reads `frame.regs.r8`, the `SavedRegs` field already existed, just unused until now). Scope cuts, both deliberate and both flagged in `README.md`'s scheduler section rather than silently punted: no priority argument, since `Task` has no priority field yet for it to set, that's a future SetPriority syscall's job; and no suspend state, a Configured thread is immediately live and schedulable the moment Configure returns, Resume/Suspend are also future syscalls. `usermode.rs`'s ring-3 self-test grows a 13th step, Configure-ing the Thread retyped in the previous entry's step 10 against the same AddressSpace the calling task already runs in, entry/stack pointing at a second hand-written embedded program (`program2_bytes`, its own `.rodata.user_program2` section) that just proves liveness with one syscall and loops forever; the old trailing `hlt` after the Retype sequence is removed, since halting there would prevent the timer from ever preempting into the newly-Configured task. Zero build warnings (`cargo build`, `cargo build --release`). Verified on BIOS QEMU via `tools/smoke-test.sh`: all 13 self-test steps pass, Configure step returns task index 5 as expected, ending in `usermode self-test: full boot sequence confirmed`. The second program's own liveness syscall didn't show up in this run; consistent with this sandbox's QEMU/TCG not reliably delivering hardware IRQ0 (see TROUBLESHOOTING.md and the 2026-07-19/07-25 timer entries), so the 8s smoke-test window likely closed before a real tick ever preempted task 0 into the new task. Not yet run in Oracle VM VirtualBox. Known gap surfaced, not solved by this feature: `gdt::set_kernel_stack` (TSS.RSP0) is still a single global value set once at boot, fine while only one ring-3 thread can ever be mid-trap at a time (true today, no real concurrency), but wrong the moment two Configured threads could both trap into ring 0 concurrently; noted in `README.md`, tracked as a future fix, not this one. Not promoted to `stable` yet.
- Retype extended to AddressSpace and Thread (`kernel/src/untyped.rs`, plus changes in `syscall.rs`/`main.rs`/`usermode.rs`): `retype`'s supported-type check widens from `Frame | CSpace` to `Frame | CSpace | AddressSpace | Thread`. New `ObjectType::AddressSpace` arm charges one bookkeeping frame from the pool (same asymmetry CSpace already uses; frame taken but not the actual backing storage), calls `unsafe { paging::new_address_space() }`, and returns its `.raw()` (PML4 physical address) as the `KernelObjectId`, matching the id semantics `abi/src/lib.rs`'s own doc comment already described before any code used them. New `ObjectType::Thread` arm charges one bookkeeping frame the same way, then pushes a new placeholder `ThreadObject` (empty struct, no fields yet) into a new `THREAD_OBJECTS` registry (mirrors `CSPACE_OBJECTS`/`register_cspace` exactly) via new `register_thread`, returns the registry index. That index is explicitly not yet the real scheduler task index `abi`'s `KernelObjectId` doc comment anticipates; reconciling the two is deferred to the Configure syscall feature, which is also what will give a retyped Thread a stack, entry point, and suspend/resume state before it's safe to add to `scheduler.rs`'s live round-robin queue. Neither `scheduler.rs` nor a `paging::AddressSpace::from_raw()` reconstruction helper is touched in this feature; the former would crash immediately (no suspend/resume state exists), the latter would be dead code today (nothing calls it until Frame.Map syscalls exist), both against the zero-build-warnings policy. `syscall.rs`'s `dispatch_untyped` rights match gains `AddressSpace => Rights::MAP` (a future Frame.Map syscall will check the target AddressSpace cap carries MAP) and `Thread => Rights::GRANT` (mirrors CSpace's precedent of GRANT as "the one op this type gates"; explicitly provisional pending the Configure/Resume/Suspend/SetPriority syscalls actually defining Thread's own per-op checks). `main.rs`'s `usermode_selftest` untyped pool grows from `UntypedObject::new(2)` to `new(4)`, since the ring-3 self-test now needs four successful retypes before hitting Exhausted. `usermode.rs`'s ring-3 Retype sequence grows from four steps to six: retype Frame (ok), CSpace (ok), AddressSpace (ok, new), Thread (ok, new), Frame again (now correctly Exhausted after four frames spent instead of two), PageTable (UnsupportedType, deliberately proving today's PageTable punt is enforced in code and not just documented). The old step 10, which retyped Thread and asserted `UnsupportedType`, is gone; that assertion would have broken the moment Thread became retypeable, so it's replaced rather than left stale. Updated `UNTYPED_SYSCALL_STEPS` (4 rows to 6), the `global_asm!` program, and every doc comment referencing the old four-step count. Zero build warnings (`cargo build`, `cargo build --release`). Verified on BIOS QEMU via `tools/smoke-test.sh`: all six Retype self-test steps pass (`result=0xfe15000`/`0x0`/`0xfe11000`/`0x0`/`0xfffffffffffffff4`/`0xfffffffffffffff3` against expected, in order), ending in `usermode self-test: full boot sequence confirmed`. Confirmed in Oracle VM VirtualBox: identical six-step sequence and outcomes (`result=0x3e1e000`/`0x0`/`0x3e1a000`/`0x0`/`0xfffffffffffffff4`/`0xfffffffffffffff3`, different physical addresses than QEMU from a different memory map, same expected codes), real hardware timer ticks confirmed via `50 ticks elapsed via hardware irq0`, same final boot-sequence-confirmed line. Promoted to `stable`.
- Task 0 address-space sync fix (`kernel/src/scheduler.rs`, `main.rs`): new `scheduler::set_current_address_space(new_as)` updates the current task's `Task.address_space` field and reloads CR3 into it in one cli/sti-bracketed step, same locking convention as `with_current_cspace`. `usermode_selftest` now calls this instead of `user_as.switch()` directly right before dropping to ring 3, so task 0's own bookkeeping and its actual CR3 never disagree. Fixes the gap logged below and in BUGS.md: without this, `tick()`'s next reload for task 0 came from a stale `Task.address_space` (still whatever `init()` set it to), reverting CR3 to the kernel's own AddressSpace the moment a real timer preemption cycled back to task 0, out from under a still-running ring-3 program. Only touches the one call site proven vulnerable; `address_space_selftest`'s own separate, transient switch (reverts before returning, runs before the scheduler starts ticking against it) is left alone. Doesn't change the interrupt-frame/stack-sharing plumbing that already lets real preemption resume a task correctly, that's proven working by the existing task_c/task_d self-test. Zero build warnings. Verified on both BIOS and UEFI in QEMU: identical ten-step self-test log, no regression. QEMU/TCG in this sandbox never delivers real IRQ0, so this fix couldn't be exercised for real preemption there. Confirmed in Oracle VM VirtualBox: full ten-step self-test now passes clean end to end, including step 10 and the final `usermode self-test: full boot sequence confirmed` line, real hardware timer ticks interleaved throughout, no fault. Closes the gap opened by the Untyped/Retype entry below (see BUGS.md, fixed). Promoted to `stable`.
- Capabilities/CSpace v0.1 (`abi` crate, `kernel/src/cspace.rs`): new `abi` crate (no_std, no deps, path dependency from `kernel/Cargo.toml`) holds `ObjectType`, `Rights` (bitfield: Read/Write/Grant/Map/Send/Receive), `Capability` (`object_ref`/`object_type`/`rights`/`badge`), `CPtr` (u32, slot 0 reserved null), `KernelObjectId` (u64 newtype), matching `docs/cores/kernel/README.md`'s spec exactly and its "Naming/versioning" rule that these live in one shared crate. Added `CSpace` as a ninth `ObjectType` row: the README's own "Boot handoff" section already grants the root task a cap to its own CSpace, but the "Object types, v0.1" table didn't list it; added the row (Ops: Insert, Delete) rather than leaving the inconsistency in place. `CSpace` (`kernel/src/cspace.rs`) is a fixed 64-slot table: `grant_root` (root grant with no parent, standing in for the real boot-handoff grant until there's a root task to receive it), `copy` (new slot, same object, rights ≤ source), `mint` (same as copy plus a new badge), `move_slot` (re-homes a cap within the same CSpace, tree links repointed), `revoke` (recursively clears every descendant then the target). `copy` and `mint` both record the new slot as a child of the source in the derivation tree; a plain copy differs from a mint only in badge/rights, not in whether revoking the source should take it down too, so `revoke`'s cascade reaches copies and mints alike. `KernelObjectId` reuses an object's existing stable identity instead of a new object heap: added `pub fn raw(&self) -> u64` to `paging::AddressSpace` (previously private `pml4_phys` field) so an AddressSpace capability's id is its own PML4 physical address. New self-test (`main.rs`, `cspace_selftest`): grants a capability over the kernel's own AddressSpace, copies it, moves the copy to a different slot (exercises `move_slot`'s tree-repointing, not just `copy`/`mint`/`revoke`), mints a third slot with narrowed rights and a distinct badge, then revokes the root and confirms all three descendant slots (the moved copy, the mint, and the root itself) went empty. Deliberately not wired to any syscall, not wired to `Task` (no component owns a CSpace yet), not integrated with Untyped/Retype (no generic object heap yet), and not integrated with Endpoint/IPC (so `move_slot`'s cross-CSpace case isn't reachable yet either); each of those is its own future feature, not folded into this one. Zero build warnings. Verified on both BIOS and UEFI in QEMU: `rose: cspace self-test: move cleared source slot ok, copy/mint object_ref match, mint narrowed rights+badge ok, revoke cascade cleared moved+minted+root ok, overall confirmed`. Not yet run in Oracle VM VirtualBox.
- CSpace syscalls (`kernel/src/syscall.rs`, plus changes in `scheduler.rs`/`idt.rs`/`usermode.rs`/`main.rs`): wires the CSpace mechanism from the previous entry up to ring 3. Every `Task` (`kernel/src/scheduler.rs`) now owns a `CSpace`, empty at creation; new `scheduler::with_current_cspace` runs a closure against whichever task is current under the scheduler lock. New `kernel/src/syscall.rs` is pure dispatch: `SYS_CSPACE_COPY`/`MINT`/`MOVE`/`REVOKE` (0x1000-0x1003, chosen well clear of the legacy self-test's 0xabcd1234/1 sentinels), args in rdi/rsi/rdx/r10, result in rax (0/positive success, negative magnitude a new `CSpaceError::code()`). `idt.rs`'s `rose_exception_handler` now takes `frame` as `&mut InterruptFrame` instead of `&*frame` (sound: the incoming pointer was already `*mut`), routes any CSpace syscall number to the new dispatcher, and writes the result back into `frame.regs.rax` before returning, which `common_stub`'s existing pop-rax/iretq path propagates straight back to ring 3; legacy sentinel syscalls keep going through the unchanged `usermode::on_syscall`. The ring-3 program in `usermode.rs` extends past its original two legacy syscalls with a fixed six-step CSpace sequence (copy, move, mint, a copy that hits `DestOccupied`, a revoke, then a copy that hits `SourceEmpty`), all hardcoded literal register values against a root capability `main.rs`'s `usermode_selftest` now grants into the task's own CSpace slot 1 before dropping to ring 3 (a boot-handoff stand-in, same pattern as `cspace_selftest`'s own `grant_root` call). New `usermode::on_cspace_syscall` checks each step against an expected-result table, logs a pass/fail line per step, and on the sixth prints an aggregated verdict and halts for good; this halt replaces the old count-two halt in `on_syscall`, since the CSpace sequence has to run after the two legacy syscalls but before the permanent halt, and `enter_user_mode` being one-way means there's no way to run a separate self-test after this one, it has to be appended into the same ring-3 program. Zero build warnings. Verified on both BIOS and UEFI in QEMU: `rose: cspace syscall self-test: step 1 copy slot1->slot2 rights=rwm ... ok` through step 6, then `sequence complete, overall confirmed`, all prior self-tests unchanged. Not yet run in Oracle VM VirtualBox.

- Untyped/Retype v0.1 (`kernel/src/untyped.rs`, plus changes in `cspace.rs`/`syscall.rs`/`idt.rs`/`usermode.rs`/`main.rs`): `UntypedObject` is a pool of individually-allocated physical frames pulled from `mem::FRAME_ALLOCATOR` up front, not a contiguous region; `retype(untyped_id, object_type)` bumps the pool's watermark and, for the only two retypeable types in v0.1, either hands back the frame's own physical address (`ObjectType::Frame`) or boxes a new `CSpace` into a module-local registry and hands back its index (`ObjectType::CSpace`), returning `UntypedError::UnsupportedType` for anything else. Added `ObjectType::to_u8`/`from_u8` to the `abi` crate (explicit match, same convention as `Rights::bits`/`from_bits`) so a syscall can pass an object type as a plain register value. New `CSpace::install_child` (`kernel/src/cspace.rs`) installs a capability into an empty slot as a child of an existing one, reusing the derivation tree `copy`/`mint` already maintain; new `CSpace::slot_is_available` checks a slot is real and empty without installing anything, since `lookup` alone can't tell an invalid cptr apart from a valid empty one and Retype needs that answer before spending a frame it can't get back. New `kernel/src/syscall.rs` `dispatch_untyped` wires the two together behind `SYS_UNTYPED_RETYPE` (0x1004): validates the source cap is really Untyped, the requested type is retypeable, and the destination slot is available, all before calling `untyped::retype`, then installs the result via `install_child`; encodes both `CSpaceError` and `UntypedError` into one return register by offsetting the latter's codes by +10 so they never collide. `idt.rs` routes `SYS_UNTYPED_RETYPE` to `dispatch_untyped` and to a new `usermode::on_untyped_syscall`, parallel to the existing CSpace branch. The usermode self-test's ring-3 program runs four more syscalls after the existing six CSpace ones: retype a Frame (ok), retype a CSpace (ok), retype a Frame again against the now-exhausted two-frame pool (`Exhausted`), retype a Thread (not retypeable, `UnsupportedType`); `main.rs`'s `usermode_selftest` grants a root Untyped cap over a fresh 2-frame pool into CSpace slot 6 ahead of time, same boot-handoff stand-in pattern as the existing slot-1 AddressSpace grant. `on_cspace_syscall`'s old final halt was removed since control now has to fall through into the Retype sequence; `on_untyped_syscall`'s own final halt is the new true end of the boot self-test chain. Scope cuts, all deliberate: no contiguous-region Untyped (that's boot handoff's job once boot handoff is real), no reclamation on revoke (frames already retyped don't return to the pool and the watermark doesn't roll back), a retyped CSpace's frame charge is bookkeeping only since the `CSpace` struct itself still lives on the kernel heap via `Box`, and freshly minted Frame caps don't do anything yet, nothing calls Map/Unmap on them. Zero build warnings. Verified on BIOS+UEFI QEMU: serial log shows `rose: untyped syscall self-test: step 1 retype slot6->slot7 Frame ... ok` through step 4, then `sequence complete, overall confirmed` and `usermode self-test: full boot sequence confirmed`. Run in Oracle VM VirtualBox: Retype's own steps 1 through 3 (slot7 Frame, slot8 CSpace, slot9 Exhausted) all returned exactly the expected results, then step 4 never ran; the CPU faulted fetching the very next ring-3 instruction, a real hardware timer preemption reverting CR3 to the kernel's own AddressSpace mid-sequence, a pre-existing scheduler/AddressSpace gap this feature's longer ring-3 program was the first to run long enough to expose (see BUGS.md, open).
