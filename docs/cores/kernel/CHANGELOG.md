# Changelog: kernel core

Date, change, why. Newest first.

## 2026-07-25

- Boot verified in Oracle VM VirtualBox, second virtualizer required by the stable promotion checklist. Serial log matches QEMU exactly: `rose: boot ok`, `rose: base revision supported`, `rose: hello, hardware`.
- Two VirtualBox-specific issues hit and logged in `TROUBLESHOOTING.md`: VM created as a 32-bit guest type masked the long-mode CPUID bit (Limine panicked with "This CPU does not support 64-bit mode"), and raw-file serial capture failed with `VERR_INVALID_NAME` when pointed at a non-local drive.
- Promoted to `stable`.
- Memory bring-up started: kernel now requests and parses Limine's memory map (`MemmapRequest`), logs every region's base/length/type over serial, and totals usable memory. Verified on both BIOS and UEFI. First step toward the physical frame allocator; no allocator yet, this is just reading and printing what the bootloader reports.
- Physical frame allocator (`kernel/src/mem.rs`): free-list over 4KiB frames built from the usable memory map regions, addressed through the HHDM offset (`HhdmRequest`) rather than assuming identity mapping. Free frames store the next-free pointer in their own first 8 bytes, so no separate bookkeeping array. Wrapped in a small spinlock (`SpinLock`, hand-rolled, not the `spin` crate) since nothing runs concurrently yet but it costs nothing to add now. Self-test on boot allocates three frames, frees the middle one, allocates again, confirms it gets the freed frame back. Verified on both BIOS and UEFI: 65186 free frames (256MiB QEMU BIOS run), 53896 free frames (UEFI run, less usable RAM due to firmware reservations). Bootloader-reclaimable regions are deliberately left out of the free list for now; reclaiming them safely needs to happen after every Limine response has been read, which isn't tracked yet.
- Memory map parsing and frame allocator verified in Oracle VM VirtualBox: 17 regions, 16043 usable frames, self-test passed with the same freed-frame-comes-back-first behavior seen in QEMU. Promoted to `stable`.
- GDT/IDT (`kernel/src/gdt.rs`, `kernel/src/idt.rs`): replaced Limine's GDT with our own (null, kernel code, kernel data, plus a minimal TSS purely for IST1). Wired all 32 CPU exception vectors with hand-written asm stubs (not the unstable `x86-interrupt` ABI): save GPRs, call a common Rust handler with a fully-known stack frame, restore, `iretq`. Double fault (#DF) is routed through TSS.ist[0] so a fault caused by a bad stack still has somewhere to report to instead of triple-faulting. Every vector logs vector/name/error code/RIP over serial and halts, except breakpoint (#BP), which logs and returns, used as a non-destructive self-test on boot. Manually verified the fatal path too during development (not part of the committed self-test): a non-canonical address correctly raised #GP, a canonical-but-unmapped address correctly raised #PF with CR2 pointing at the exact faulting address, error code decoded correctly (0x2 = write, kernel mode, not-present). Verified on both BIOS and UEFI in QEMU.
- Page tables (`kernel/src/paging.rs`): kernel now builds and switches to its own 4-level x86_64 page tables instead of running on Limine's indefinitely. Kernel image mapped section-by-section using the linker-provided bounds (`__text_start/_end`, `__rodata_start/_end`, `__data_start`, `__kernel_start/_end` in `linker.ld`) and the physical/virtual base from Limine's `ExecutableAddressRequest`: text is R+X, rodata is R-only, data+bss is R+W+NX. HHDM remapped through the same offset Limine gave us, for usable and bootloader-reclaimable memory, using 2MiB pages for aligned bulk and 4K pages at the edges. EFER.NXE turned on explicitly rather than assumed. `map_page`/`unmap_page` added as the general entry points for anything that needs a mapping after this point, backed by a single active-PML4 pointer since there's only one address space right now. Self-test on boot: allocate a frame, map it at a throwaway virtual address, write a pattern through it, read it back, unmap, return the frame to the allocator. Hit one bug during bring-up (boot stack unmapped after the CR3 switch, causing an immediate double fault); see `BUGS.md`. Verified on both BIOS and UEFI in QEMU; VirtualBox verification not yet done for this or for GDT/IDT, both still only on `main`.
- Kernel heap (`kernel/src/heap.rs`): fixed 1MiB region, eagerly mapped in full at init via `paging::map_page`, one frame per page. Free-list first-fit allocator, same metadata-lives-in-the-freed-memory approach as the frame allocator: every block starts with an 8-byte size header, free blocks additionally store the next free block's address in their own usable area. Blocks split on alloc when the leftover is worth keeping as its own block; no coalescing on dealloc, an accepted v0.1 tradeoff (see file header comment). Wired up as `#[global_allocator]`, backs `extern crate alloc` kernel-wide. Only guarantees 8-byte alignment; anything requesting more fails alloc outright rather than silently violating it, nothing needs more yet. Self-test on boot allocates a `Box<u64>` and a `Vec<u64>` grown past its initial capacity (forces a realloc), checks the values, then drops both and confirms allocated-byte count returns to 0. Observed 48 bytes of the original 1048568 free bytes not returning after the self-test (1048520 free after drop) — expected fragmentation from split-block headers left behind by the Vec's growth reallocations, not a bug, direct consequence of no coalescing. Verified on both BIOS and UEFI in QEMU; not yet in VirtualBox, still only on `main`.

## 2026-07-19

- v0.1 spec drafted: capability model, CSpace, object types, IPC format, address space model, boot handoff, scheduler policy.
- First code: kernel entry point, COM1 serial driver, panic handler. Boots via Limine (protocol requests + base revision check) on both BIOS and UEFI in QEMU.
- Milestone: "Boot to Hello, Rose in QEMU" (ground-zero step 2) reached. Serial output confirmed: `rose: boot ok`, `rose: base revision supported`, `rose: hello, hardware`.
- Smoke test script (`tools/smoke-test.sh`) added and passing: builds, boots headless, greps serial log for expected line.
- Five toolchain/boot issues hit and logged in `TROUBLESHOOTING.md`: custom json target needing an unstable cargo flag (switched to built-in `x86_64-unknown-none` target), limine crate import path, soft-float target-feature conflict, bootloader binary too old for the crate's protocol revision, OVMF `-bios` vs `-drive if=pflash` for UEFI testing.
