# Changelog: kernel core

Date, change, why. Newest first.

## 2026-08-01

- Capabilities/CSpace v0.1 (`abi` crate, `kernel/src/cspace.rs`): new `abi` crate (no_std, no deps, path dependency from `kernel/Cargo.toml`) holds `ObjectType`, `Rights` (bitfield: Read/Write/Grant/Map/Send/Receive), `Capability` (`object_ref`/`object_type`/`rights`/`badge`), `CPtr` (u32, slot 0 reserved null), `KernelObjectId` (u64 newtype), matching `docs/cores/kernel/README.md`'s spec exactly and its "Naming/versioning" rule that these live in one shared crate. Added `CSpace` as a ninth `ObjectType` row: the README's own "Boot handoff" section already grants the root task a cap to its own CSpace, but the "Object types, v0.1" table didn't list it; added the row (Ops: Insert, Delete) rather than leaving the inconsistency in place. `CSpace` (`kernel/src/cspace.rs`) is a fixed 64-slot table: `grant_root` (root grant with no parent, standing in for the real boot-handoff grant until there's a root task to receive it), `copy` (new slot, same object, rights ≤ source), `mint` (same as copy plus a new badge), `move_slot` (re-homes a cap within the same CSpace, tree links repointed), `revoke` (recursively clears every descendant then the target). `copy` and `mint` both record the new slot as a child of the source in the derivation tree; a plain copy differs from a mint only in badge/rights, not in whether revoking the source should take it down too, so `revoke`'s cascade reaches copies and mints alike. `KernelObjectId` reuses an object's existing stable identity instead of a new object heap: added `pub fn raw(&self) -> u64` to `paging::AddressSpace` (previously private `pml4_phys` field) so an AddressSpace capability's id is its own PML4 physical address. New self-test (`main.rs`, `cspace_selftest`): grants a capability over the kernel's own AddressSpace, copies it, moves the copy to a different slot (exercises `move_slot`'s tree-repointing, not just `copy`/`mint`/`revoke`), mints a third slot with narrowed rights and a distinct badge, then revokes the root and confirms all three descendant slots (the moved copy, the mint, and the root itself) went empty. Deliberately not wired to any syscall, not wired to `Task` (no component owns a CSpace yet), not integrated with Untyped/Retype (no generic object heap yet), and not integrated with Endpoint/IPC (so `move_slot`'s cross-CSpace case isn't reachable yet either); each of those is its own future feature, not folded into this one. Zero build warnings. Verified on both BIOS and UEFI in QEMU: `rose: cspace self-test: move cleared source slot ok, copy/mint object_ref match, mint narrowed rights+badge ok, revoke cascade cleared moved+minted+root ok, overall confirmed`. Not yet run in Oracle VM VirtualBox.

## 2026-07-25

- Scheduler is address-space-aware (`kernel/src/scheduler.rs`): `Task` gained an `address_space: AddressSpace` field. `spawn(entry)` now just calls the new `spawn_in(entry, paging::kernel_address_space())`; `spawn_in(entry, address_space)` is the general form for a task that should run somewhere else. `tick()` and `yield_now()` both look up the incoming task's `AddressSpace` before dropping the scheduler lock, then call `next_as.switch()` immediately before the existing naked-asm `context_switch`, unconditionally for now (no check for "already the same AS, skip the reload"; `AddressSpace::switch()` does a full TLB flush regardless of whether the PML4 actually changed, so the only thing a same-AS skip would save is the `mov cr3` itself, not worth the added AddressSpace-equality plumbing yet). New self-test (`main.rs`, `scheduled_address_space_selftest`, plus `task_c`/`task_d`): builds two AddressSpaces, maps the same virtual address in each to a different physical frame with a different pattern, spawns one task per AddressSpace via `spawn_in`, lets them run interleaved with the existing scheduler self-test's `task_a`/`task_b` (both looping forever after their own self-test finishes, same as before) for several real yields each, then confirms both tasks only ever read back their own pattern. This is the first proof that CR3 actually follows the task under real scheduling and preemption, not just a single manual switch (that was `address_space_selftest`'s job, still in place, unchanged). No teardown for `task_c`/`task_d`'s AddressSpaces or test frames, same reasoning as `task_a`/`task_b` never exiting: they loop forever, so the mappings need to stay live anyway. Closes the gap flagged in this file's own address-spaces entry below and in `README.md`'s "Address spaces" spec section (updated to note it's closed): before this, a scheduled task's CR3 never changed regardless of what `AddressSpace` its `Task` claimed, since nothing ever loaded it. Doesn't touch capabilities/CSpace at all; a task in its own AddressSpace is still plain kernel-linked Rust with no syscall boundary, that's the next layer. Zero build warnings. Verified on both BIOS and UEFI in QEMU, identical serial log. Confirmed in Oracle VM VirtualBox: identical serial log, isolation across scheduling confirmed, with real hardware timer ticks interleaved in throughout (`50 ticks elapsed via hardware irq0, 510ms since boot`), usermode self-test unaffected. Promoted to `stable`.
- Address spaces (`kernel/src/paging.rs`): the old single implicit table set is now an `AddressSpace` handle (a PML4 physical address). `kernel_address_space()` returns the kernel's own, set once by `init()`. `new_address_space()` allocates a fresh PML4 and copies the kernel's PML4 entries 256..512 (HHDM plus the kernel image) into it, leaving the lower 256 entries zeroed; every AddressSpace can therefore always run kernel code and touch HHDM regardless of which one CR3 currently holds, present but supervisor-only so ring 3 can't reach it. `map_page`/`unmap_page` are now methods on `AddressSpace` instead of free functions operating on one global pointer; added `switch()` (loads CR3) and a new read-only primitive, `is_mapped()`, a table walk that checks PRESENT without ever dereferencing the target address, safe to call on something that would fault if actually touched. `phys_to_virt` made `pub`, since writing into a not-yet-active AddressSpace's frame has to go through its permanent HHDM alias rather than through a virtual address CR3 doesn't point at yet. `usermode_selftest` (`main.rs`) now builds its own `AddressSpace` via `new_address_space()` instead of reusing the kernel's, and writes the embedded program into the code frame through `phys_to_virt` instead of through `CODE_VADDR` directly, which also means the code page can be mapped R+X+U from the very start with no WRITABLE step ever needed, obsoleting (not deleting, see BUGS.md) the WRITABLE-then-remap workaround from the ring3 feature. A new boot self-test, `address_space_selftest`, builds a second AddressSpace, proves via `is_mapped()` that a page mapped only in it is invisible to the kernel's own AddressSpace and vice versa, then does the project's first reversible AS switch (entirely in ring 0): switches CR3 into it, writes a pattern through the now-valid pointer, reads it back, switches back to the kernel. No AddressSpace teardown/free mechanism, matching the existing no-coalescing/no-task-exit precedent, documented as a scope cut in `README.md`, not an oversight. Also documented in `README.md`: the kernel/HHDM upper half being shared present-but-supervisor-only into every AddressSpace is real ring-3 isolation but not yet the stricter "structurally unmappable" goal the doc states; and the scheduler's context switch still doesn't touch CR3 at all, fine today since every task runs in the kernel's own AddressSpace, but blocking multi-component scheduling later. Zero build warnings. Verified on both BIOS and UEFI in QEMU: isolation confirmed, write/readback match, usermode self-test passes identically through the new separate AddressSpace. Confirmed in Oracle VM VirtualBox: identical serial log, isolation confirmed, write/readback match, real hardware timer ticks as expected (`50 ticks elapsed via hardware irq0, 510ms since boot`), usermode self-test identical two-syscall sequence and halt line. Promoted to `stable`.
- Ring 3 / user mode (`kernel/src/usermode.rs`, plus new bits in `gdt.rs`/`paging.rs`/`idt.rs`): first code that ever runs outside CPL0. GDT gained a user code selector (0x28) and a user data selector (0x30), both DPL=3, RPL=3 baked into the selector constants; also added `gdt::set_kernel_stack` to point TSS.rsp0 at a scratch stack before the first ring3->ring0 trap. Paging gained `PAGE_USER`, and `next_level()` now sets it on every intermediate table it allocates, not just the leaf: x86 ANDs the U/S bit across the whole walk, so a leaf's own USER bit is meaningless if a PML4E/PDPTE/PDE above it lacks it. IDT gained vector 0x80 as a DPL=3 interrupt gate (`Entry::set_user`, only used for this one vector, every other gate stays DPL=0) so a ring-3 `int 0x80` doesn't #GP; `rose_exception_handler` dispatches it to `usermode::on_syscall` ahead of the general exception path, same pattern as the existing IRQ0 special case. `usermode.rs` embeds a tiny hand-written asm program (`global_asm!`, its own `.rodata.user_program` section with start/end linker symbols) that does two `int 0x80` calls then parks in an infinite jump; `enter_user_mode` drops to ring 3 via a manually built iretq frame and never returns in this cut, `on_syscall` logs each call and halts for good on the second one. `usermode_selftest` in `main.rs` maps a code page and a stack page as USER, copies the program in, sets rsp0, and calls `enter_user_mode`; it's now the last thing `kernel_main` calls, replacing the old trailing `hlt` loop (would've been unreachable code once this diverges). No process model, no return-to-kernel path, no second user task; all documented scope cuts for v0.1, see usermode.rs module docs. Hit one real bug during bring-up: the code page's first write (copying the program in) needed WRITABLE set even though the write came from CPL0, since CR0.WP doesn't care about ring, only about the PTE's own writable bit; fixed by mapping writable for the copy then re-mapping read-only+exec before ring 3 ever runs. See `BUGS.md`. Zero build warnings. Verified on both BIOS and UEFI in QEMU: `rose: usermode self-test: syscall #1 from ring 3, rax=0xabcd1234` then `#2` with `rax=0x1`, then the confirmed-halt line, right after the existing scheduler self-test line. Confirmed in Oracle VM VirtualBox too, identical two-syscall sequence and halt line. Promoted to `stable`.
- Boot verified in Oracle VM VirtualBox, second virtualizer required by the stable promotion checklist. Serial log matches QEMU exactly: `rose: boot ok`, `rose: base revision supported`, `rose: hello, hardware`.
- Two VirtualBox-specific issues hit and logged in `TROUBLESHOOTING.md`: VM created as a 32-bit guest type masked the long-mode CPUID bit (Limine panicked with "This CPU does not support 64-bit mode"), and raw-file serial capture failed with `VERR_INVALID_NAME` when pointed at a non-local drive.
- Promoted to `stable`.
- Memory bring-up started: kernel now requests and parses Limine's memory map (`MemmapRequest`), logs every region's base/length/type over serial, and totals usable memory. Verified on both BIOS and UEFI. First step toward the physical frame allocator; no allocator yet, this is just reading and printing what the bootloader reports.
- Physical frame allocator (`kernel/src/mem.rs`): free-list over 4KiB frames built from the usable memory map regions, addressed through the HHDM offset (`HhdmRequest`) rather than assuming identity mapping. Free frames store the next-free pointer in their own first 8 bytes, so no separate bookkeeping array. Wrapped in a small spinlock (`SpinLock`, hand-rolled, not the `spin` crate) since nothing runs concurrently yet but it costs nothing to add now. Self-test on boot allocates three frames, frees the middle one, allocates again, confirms it gets the freed frame back. Verified on both BIOS and UEFI: 65186 free frames (256MiB QEMU BIOS run), 53896 free frames (UEFI run, less usable RAM due to firmware reservations). Bootloader-reclaimable regions are deliberately left out of the free list for now; reclaiming them safely needs to happen after every Limine response has been read, which isn't tracked yet.
- Memory map parsing and frame allocator verified in Oracle VM VirtualBox: 17 regions, 16043 usable frames, self-test passed with the same freed-frame-comes-back-first behavior seen in QEMU. Promoted to `stable`.
- GDT/IDT (`kernel/src/gdt.rs`, `kernel/src/idt.rs`): replaced Limine's GDT with our own (null, kernel code, kernel data, plus a minimal TSS purely for IST1). Wired all 32 CPU exception vectors with hand-written asm stubs (not the unstable `x86-interrupt` ABI): save GPRs, call a common Rust handler with a fully-known stack frame, restore, `iretq`. Double fault (#DF) is routed through TSS.ist[0] so a fault caused by a bad stack still has somewhere to report to instead of triple-faulting. Every vector logs vector/name/error code/RIP over serial and halts, except breakpoint (#BP), which logs and returns, used as a non-destructive self-test on boot. Manually verified the fatal path too during development (not part of the committed self-test): a non-canonical address correctly raised #GP, a canonical-but-unmapped address correctly raised #PF with CR2 pointing at the exact faulting address, error code decoded correctly (0x2 = write, kernel mode, not-present). Verified on both BIOS and UEFI in QEMU, and in Oracle VM VirtualBox (breakpoint self-test log matches exactly). Promoted to `stable`.
- Page tables (`kernel/src/paging.rs`): kernel now builds and switches to its own 4-level x86_64 page tables instead of running on Limine's indefinitely. Kernel image mapped section-by-section using the linker-provided bounds (`__text_start/_end`, `__rodata_start/_end`, `__data_start`, `__kernel_start/_end` in `linker.ld`) and the physical/virtual base from Limine's `ExecutableAddressRequest`: text is R+X, rodata is R-only, data+bss is R+W+NX. HHDM remapped through the same offset Limine gave us, for usable and bootloader-reclaimable memory, using 2MiB pages for aligned bulk and 4K pages at the edges. EFER.NXE turned on explicitly rather than assumed. `map_page`/`unmap_page` added as the general entry points for anything that needs a mapping after this point, backed by a single active-PML4 pointer since there's only one address space right now. Self-test on boot: allocate a frame, map it at a throwaway virtual address, write a pattern through it, read it back, unmap, return the frame to the allocator. Hit one bug during bring-up (boot stack unmapped after the CR3 switch, causing an immediate double fault); see `BUGS.md`. Verified on both BIOS and UEFI in QEMU, and in Oracle VM VirtualBox (map/write/read/unmap self-test log matches exactly). Promoted to `stable`.
- Kernel heap (`kernel/src/heap.rs`): fixed 1MiB region, eagerly mapped in full at init via `paging::map_page`, one frame per page. Free-list first-fit allocator, same metadata-lives-in-the-freed-memory approach as the frame allocator: every block starts with an 8-byte size header, free blocks additionally store the next free block's address in their own usable area. Blocks split on alloc when the leftover is worth keeping as its own block; no coalescing on dealloc, an accepted v0.1 tradeoff (see file header comment). Wired up as `#[global_allocator]`, backs `extern crate alloc` kernel-wide. Only guarantees 8-byte alignment; anything requesting more fails alloc outright rather than silently violating it, nothing needs more yet. Self-test on boot allocates a `Box<u64>` and a `Vec<u64>` grown past its initial capacity (forces a realloc), checks the values, then drops both and confirms allocated-byte count returns to 0. Observed 48 bytes of the original 1048568 free bytes not returning after the self-test (1048520 free after drop); expected fragmentation from split-block headers left behind by the Vec's growth reallocations, not a bug, direct consequence of no coalescing. Verified on both BIOS and UEFI in QEMU, and in Oracle VM VirtualBox (identical free-byte counts, same self-test log). Promoted to `stable`.
- PIC + PIT timer (`kernel/src/pic.rs`, `kernel/src/timer.rs`): 8259 PIC remapped so IRQ0-7 land on vectors 32-39 and IRQ8-15 on 40-47, all lines masked except IRQ0. 8253/8254 PIT channel 0 programmed for 100Hz (mode 3, divisor 11931) and `sti` executed. IDT vector 32 dispatches to `timer::on_tick` (atomic tick counter) then sends EOI, ahead of the general exception-logging path in `idt.rs`. Hit two real issues during bring-up. First: hardware IRQ0 never reaches the CPU in this sandbox's QEMU/TCG (PIC IRR shows it permanently pending, `-d int` trace shows zero servicing events), even though PIC/PIT programming, IF flag, and the entire IDT/EOI/tick-counting path are all independently verified correct, the last part via a software-triggered `int 0x20` which dispatches instantly. Confirmed as a sandbox-only limitation, not a kernel bug, by booting in Oracle VM VirtualBox: the tick handler fired immediately there and the counter advanced normally; logged in `TROUBLESHOOTING.md`. Second, found from that same VirtualBox run: `timer_selftest`'s RDTSC timeout used a 500MHz frequency floor when it needed a ceiling, so on VirtualBox's real multi-GHz host it bailed out in a couple hundred ms instead of the intended 2s and misreported a working timer as absent; fixed by switching to an 8GHz assumed ceiling, logged in `BUGS.md`. Re-ran the fixed build in Oracle VM VirtualBox: self-test now passes clean, `50 ticks elapsed via hardware irq0, 510ms since boot`, full end-to-end confirmation. Verified on both BIOS and UEFI in QEMU (sandbox-limited software-int fallback path, expected) and fully verified in Oracle VM VirtualBox (real hardware ticks, clean pass). Promoted to `stable`.
- Scheduler v0.1 (`kernel/src/scheduler.rs`): task struct (saved rsp + owned stack), hand-written xv6-style `context_switch` (naked asm, save/restore rbx/rbp/r12-r15, swap rsp, `ret`), single round-robin queue, fixed 5-tick (50ms) timeslice. Two entry points: `tick()` from the timer IRQ (EOI now sent before `on_tick`/`scheduler::tick` run, reordered in `idt.rs`, since a switch inside the handler means this call frame may not resume for many ticks and the PIC's in-service bit can't be left set that whole time), and `yield_now()` for voluntary switches (hand-bracketed with `cli`/`sti`, required to avoid a single-CPU spinlock deadlock against a real tick landing mid-yield, and to re-enable interrupts after a `ret`-based resume that never touches RFLAGS). Freshly spawned tasks resume into a small naked `task_trampoline` that re-enables interrupts and calls the entry function; no task-exit mechanism yet, matches the heap's earlier "no coalescing" style scope cut. Self-test spawns two tasks that each count to 10 with a `yield_now()` between increments, deterministic and portable since it's fully cooperative; real hardware ticks (where they land) interleave through the same round-robin rule with no special-casing needed. Hit three real bugs during bring-up, all fixed and logged in `BUGS.md`: a fabricated stack frame written in the wrong order sent a new task's first `ret` to address 0 (page fault); a self-test task that stopped yielding after finishing froze the entire round-robin ring, including task 0's own wait loop; and a boot-order bug only reachable on real hardware, where `scheduler::init()` ran after interrupts were already enabled, so the first hardware tick on a VirtualBox boot landed on an empty task queue and panicked on a modulo by zero (this sandbox's QEMU/TCG never delivers hardware IRQ0, so it never hit this). Fixed by registering task 0 before `pic::init()`/`timer::init()` run, plus a defensive empty-queue guard in `tick()`. Verified on both BIOS and UEFI in QEMU: `task_a=10 task_b=10 switches=31`, zero build warnings. Boot-order fix confirmed in Oracle VM VirtualBox: same result, no panic. Promoted to `stable`.

- Timer self-test countdown: prints "Ns remaining..." to serial once per elapsed chunk of the existing 2s wait budget, so a real multi-second wait (possible on hosts slower than the assumed TSC ceiling, see the comment above `timer_selftest`) doesn't look identical to a hang. Ticks against the same TSC/ceiling math the wait's own bailout already used, not a real-time clock, so the printed countdown runs slower than an actual second per step on a slow host; acceptable since the point is visible progress, not precision. Never fires on working hardware, since a real irq0 finishes the 50-tick wait in ~500ms, well under the first chunk boundary; only visible in this sandbox's software-int-fallback path. Also added a matching countdown to `tools/smoke-test.sh`'s fixed 8s boot wait, printed to the terminal instead of blocking silently.
